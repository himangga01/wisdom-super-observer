## Sid and token-ID key state

Response extraction `N:0x2d28d8` (`native-security:38–220`) reads **string `sid` and `tokenId`** from operation data. Nonempty sid and a manager cause `setAESEncryptKey(sid,tokenId)`; the extractor reports 1 after calling this **void** setter. That result does not certify key validity. Generic callback extraction can run on unsuccessful business replies before Java classification. A protected web implementation must only admit credentials/key state under the accepted login/renewal result and current identity scope.

The complete setter `N:0x2d893c` (`native-security:221–567`) locks and proceeds in this order:

1. Empty sid exits without changing state. A **nonempty tokenId equal to cached tokenId** exits before key lookup or sid decryption. A changed sid under the same nonempty tokenId is ignored. Empty tokenId bypasses the equality shortcut.
2. Use nonempty temporary MD5-password state. If empty, call `getAESEncryptKey`; if that also yields empty, exit before clearing the current key or changing tokenId. Otherwise copy the existing key's **text representation** into temporary state. Password login uses old password's lowercase MD5 hex; provider login uses lowercase MD5(provider code); registration's earlier MD5(code) state remains a separate established behavior. No account-token-derived AES key exists.
3. Clear the in-memory key at manager offset `0x130`. Treat **sid ending in `=` as already Base64**; otherwise Base64-encode its raw bytes before passing to the decrypt helper. Treat **temporary key text ending in `=` as Base64 to decode**; otherwise its text bytes are the AES key. This is an exact trailing-character heuristic, not validation of arbitrary Base64. A 24-byte value's 32-character unpadded Base64 text is therefore used as a raw 32-byte key by this branch.
4. Only a temporary material length of **16,24,32 bytes** invokes the helper. `N:0x2df1e4` Base64-decodes sid, zero-extends incomplete ciphertext to a 16-byte boundary, AES-decrypts independent blocks (**ECB**) and Base64-encodes the entire aligned decrypted bytes. It does **not** remove PKCS7, trim trailing NULs, truncate to an announced key length or validate decrypted key contents. Setter retains this returned **Base64 text** as the new in-memory key.
5. A nonempty returned text is persisted through the SDK write callback and clears temporary state. An empty returned text is not persisted and leaves temporary state present. After reaching decryption, tokenId is assigned even if the result is empty. Consequently, a failed derivation may leave empty in-memory state, old persisted material and a new cached tokenId. Matching that nonempty ID later skips the setter. This is source behavior, not an acceptable web admission guarantee.

Getter `N:0x2d8fe4` (`native-security:568–644`) returns nonempty in-memory text, or loads the key through the configured SDK read callback when available. The stored key is not intrinsically namespaced by tokenId in this function. A getter can reload old persisted material following a failed setter. The web must scope protected key state to current USER identity, region, brand, credential generation and token association; it must not copy the APK's process-global cross-identity fallback or treat stale persisted bytes as fresh admission.

For valid, aligned inputs the source-equivalent formula is:

`sessionKeyText = Base64(AES-ECB-decrypt(keyMaterial(tempOrPreviousKeyText), decodeSid(sid)))`

where `keyMaterial` decodes only text ending in `=`, and `decodeSid` decodes only sid ending in `=`; other sid bytes enter unchanged after encode/decode normalization. Zero-extension is retained for incomplete native input. **Web policy** should reject malformed/noncanonical Base64, incomplete ciphertext, absent/wrong-length final material and failed business responses before dispatching a password write. Native tolerates several of these cases or leaves ambiguous state; that is not source evidence of server acceptance.

Password update normalizes the 32 ASCII lowercase-MD5 bytes, encrypts ECB with key material selected by the same trailing-`=` rule, and Base64-encodes the 32 ciphertext bytes (`N:0x34857c`, `0x3176e8`). No extra padding block, IV or oldPassword field is emitted. Original ARM64 instructions at `0x2df3b8–0x2df3c4` and `0x2dee7c–0x2dee8c` use **`FRINTP`** before fixed-point `FCVTZS #2`: Base64 length is `4*ceil(n/3)` and buffer size is that plus one. Ghidra's C expression resembling floor is incorrect. `N:0x2df104` clips writes to available capacity; the correct capacity preserves full standard Base64, including 44 characters for 32 bytes.

Eight private **invented** fixtures cover raw and represented 16/24/32-byte temporary material, password-MD5 first admission and previous-key rotation. Python cryptography and Windows .NET AES independently agree on admitted Base64 text and password ciphertext. A 24-byte invented plaintext retains eight zero bytes after block alignment; no unpadding was silently applied. Source branch tracing establishes tokenId/cache behavior; the fixtures validate crypto math, not C++ concurrency, SDK persistence, malformed BIO behavior, native execution or any real server response. No decoded raw key or SDK registration constant is published here.
