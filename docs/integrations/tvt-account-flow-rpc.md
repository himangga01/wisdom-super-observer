# Account-flow RPC transport and worker composition

Analysis date: 2026-10-02. Source baseline: published
`93f818307271047d69ca447f3782d432e8d97905`, plus the nine W06 RPC files
recorded in the private review packet. This describes implemented transport and
configuration. Protected SQL authorization and APK/upstream equivalence require
their separate reviewed evidence. `MATCHED=0`; `release_ready=false`.

## Transport contract

The additive `wso.tvt.account.v1.FlowBridgeV1` service has eight fixed methods:

| RPC / Python worker method | Exact request body | Exact public result |
| --- | --- | --- |
| Start / start | AccountFlowStart | AccountFlowView |
| State / state | AccountFlowReference | AccountFlowView |
| Existence / existence | AccountFlowReference | AccountFlowView |
| Image / image | AccountFlowReference | AccountFlowView |
| IssueCode / issue_code | AccountDynamicCodeRequest | AccountFlowView |
| Register / register | AccountRegistrationSubmit | AccountFlowView |
| Recover / recover | AccountRecoverySubmit | AccountFlowView |
| Cancel / cancel | AccountFlowCancel | AccountFlowView |

Each request contains the existing `RpcContext` at field 1 and `private_json`
at field 2. `FlowReply` contains `public_json` at field 1 or a fixed
`failure_code` at field 2, exclusively. Version remains 1. Existing
AccountBridgeV1 method names, message numbers and reserved context fields 5–15
are unchanged. Neither client nor server selects an arbitrary worker method
from input. Stubs are generated by the pinned existing generator.

The existing verified mTLS channel carries both services. A server admits only
one authenticated client SAN from its configured allowlist; TLS identity is
checked before payload parsing or worker admission. Metadata, local flow UUIDs,
challenge references and JSON fields grant no authority. API code must issue
the one-use ticket within its authenticated SQL transaction, commit it, then
call the typed RPC. SQL checks of current session, actor, tenant, consent,
generation, operation and purpose remain the protected worker's responsibility.

Private JSON uses explicit extraction of each reviewed SecretStr field. Flow
start preserves omitted email country_code and rejects explicitly null email
country_code. Phone mode preserves country_code and the local account separately
for the protected worker's native binding. Public output is decoded again using
closed AccountFlowView validation, duplicate-key rejection and exact request_id.
Selection, purpose and any submitted flow_id must also match the response.
Unknown fields, unknown protobuf fields, invalid enums, unsupported native BMP
input, malformed JSON, oversized payloads and invalid context are rejected.
There are no private response texts, secret exception inputs, SQL handles or
key values in the public result. Flow failures have their own fixed allowlist;
the old account failure vocabulary is unchanged.

## Deadline, capacity and ownership

The single original call budget includes TLS, queueing, decoding, execution,
serialization and delivery. Neither service retries automatically. Both share
the existing callback registry, capacity, correlation history and SessionPool.
Cancellation stops delivery while a dispatched call retains capacity until it
settles. A deadline after dispatch or an abandoned/closed late result becomes
UNKNOWN_OUTCOME. Transport uncertainty does not prove a native write failed.

Client close retires the registry and closes its shared channel once. Server
close stops admission immediately and uses the existing bounded drain grace;
disposal waits for active calls to settle. Worker shutdown closes its flow
executor with one 1000 ms cleanup budget, then admission and old token vault,
independently and once. A failed cleanup retains the epoch's disposer and worker
references and makes server close return false. Repeating close does not rerun
cleanup or convert quarantine into success. Startup creation, registration,
TLS binding and native start failures retire already owned resources with fixed
public errors. No configuration exceptions are logged.

## Explicit worker configuration

Both settings below must be absent to preserve the old worker with flows disabled.
In that mode, the authenticated FlowBridgeV1 returns ACCOUNT_UNAVAILABLE while
AccountBridgeV1 remains available. Either setting present requires both valid
settings; partial, blank, unreadable or invalid configuration fails startup.

| Worker-only setting | Required value |
| --- | --- |
| WSO_TVT_ACCOUNT_FLOW_PROFILE_FILE | UTF-8 JSON list, 1–64 entries, at most 65,536 bytes |
| WSO_TVT_ACCOUNT_FLOW_KEY_FILE | Stable private file containing exactly 32 raw bytes |

A profile entry is a closed object containing string `region`, `brand`,
`default_domain`, and optional string `terminal_id`. Duplicate JSON keys and
duplicate selection pairs are rejected. Pairs must exactly equal the trusted
AccountEndpoints loaded by the existing WSO_TVT_ACCOUNT_PROFILE_FILE. Strings
are bounded native BMP input of at most 4096 UTF-8 bytes. default_domain can be
explicitly empty, following the APK contract. It is the unhashed domain input;
customer_mark is a different value and cannot substitute for it. Origin,
language, country, app_version and customer_app_id are trusted endpoint settings,
never browser inputs. No key or profile is generated by startup.

Deploy the binding key through the existing worker secret delivery process with
private Windows ACLs or equivalent owner-only file access. The loader bounds and
validates bytes; it does not audit operating-system ACLs or implement a KMS.
Keep the key stable for the lifetime of admitted flows. The factory passes
`sha256(binding_key).hexdigest()` to FlowAdmission as key_commitment and constructs
AccountFlowWorkerExecutor only when explicit configuration is supplied.

Before enabling flows, the separately reviewed protected SQL deployment must
configure its operation policy with the same key_commitment and explicit consent
mapping for the intended region/brand and registration/recovery operations.
Use that protected deployment's policy/consent procedures and role boundary;
do not insert authority values from browser input. Key changes require coordinated
policy commitment changes and retirement of flows admitted under the previous
key. This RPC change does not provision SQL policy, consent, secrets or deployment
configuration. The API client factory still reads only its existing endpoint,
CA file, client certificate file and client key file; it never loads flow
profiles, a binding key, a worker database URL or a protected executor.

## Verification and limits

The final owned suite passed 59 tests with zero skips; the three affected existing
bridge suites passed 57 tests with zero skips. Scoped Ruff and format checks
passed for five handwritten/test files; strict typing passed for four handwritten
source files. Two pinned stub regenerations reproduced identical bytes and
left all 24 observed generated files unchanged. Focused tests exercise private serialization, phone binding, omitted/null cases,
closed payloads and frames, purpose and result validation, fixed error codes,
verified in-process TLS for all eight methods, wrong SAN/untrusted CA denial,
original deadlines, capacity retention, late completion, once-only disposal,
startup/shutdown failure handling and disabled/partial/configured worker startup.
Worker-factory tests replace SQL admission, old vault and protected executor
with deterministic lifecycle doubles; they do not execute protected authority.
The three existing bridge contract/reconnect/mTLS suites verify affected shared
behavior, including compatibility of the original six operations. Ruff, scoped
strict mypy and deterministic generation results are recorded with exact argv,
stdout, stderr, exit codes and frozen source hashes in the private W06 packet.
The typecheck treats only runtime-generated protobuf descriptor modules as
untyped imports; handwritten bridge source remains strict.

These synthetic RPC successes establish transport behavior only. No real
protected flow executor, PostgreSQL flow admission, HTTP/native account operation,
vendor interaction, device, browser flow or live account write was executed by
this task. Protected core bytes were still awaiting independent root review
during implementation. API routes and React integration are separate work.
