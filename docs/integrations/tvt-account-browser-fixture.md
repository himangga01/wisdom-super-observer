# Owned account browser fixture

This explicit test fixture runs Chrome → HTTPS Next same-origin proxy → HTTPS FastAPI → PostgreSQL one-use account tickets → a separate mTLS worker process → the concrete executor, token vault and AccountClient → an owned HTTPS decoded-protocol server. It uses synthetic accounts only. It does not establish APK parity, real account/device interoperability, OIDC provider exchange or production deployment acceptance.

## Running

Use the locked workspace dependencies and installed Chrome. On this managed Windows development machine, silently source `.superpowers/runtime/postgresql17/env.ps1` once, then run:

```powershell
node scripts/test-tvt-account/server.mjs --browser
```

The owned runner executes desktop and mobile sequentially in two independent real Playwright lifetimes, each with a new private context and owned PostgreSQL database. It waits for successful teardown/process exit before starting the next viewport and stops immediately on failure. The config requires the runner's explicit viewport selector, so the earlier unsafe shared-lifetime invocation cannot silently run. This retains strict rotation refusal: migration 0007 keeps a redeemed standalone check ticket valid until its original 30-second expiry even after TVT logout. No ticket is deleted early or ignored to let the next case rotate. The Playwright configuration activates the fixture explicitly, uses one worker, no retries, Chrome desktop 1440×900 and mobile 390×844, and a fixed HTTPS origin `https://localhost:3543`. A foreign listener is never reused or killed. Startup is bounded at 60 seconds; cleanup uses a 120-second reporting deadline (Next up to 20 seconds, then Python up to 100 seconds within the same deadline) and a 130-second outer observer. Next alone may be terminated via its exact owned handle after 15 seconds, with 5 seconds to reap. Python is never killed by that parent deadline. Its API cleanup retains 10 seconds plus 5 seconds for termination/reap; the accepted worker cleanup retains 15 plus 5 seconds, then upstream closure and guarded database cleanup. If an owned child exceeds the reporting deadline, an incomplete receipt is written and the Node custodian retains its original handle until actual settlement. The observer fails instead of killing the custodian or claiming resources absent. Receipt event history records the deadline failure and eventual settlement. These are reporting deadlines; unavailable PostgreSQL or a stuck OS process may require longer custody. Playwright has a 420-second overall budget covering startup, two 90-second cases, cleanup and margin. `globalSetup` returns a cooperative teardown function using the owned child stdin. This deliberately avoids Playwright's Windows `webServer` force-tree termination, which would bypass Python database cleanup. Host-only safety contracts are `python -m pytest tests/contract/test_account_web_fixture.py -q` and require no database environment.

The `account-browser.yml` workflow is source only until root dispatches it. It pins Ubuntu 24.04, Python 3.12.10, Node 24.21.0, pnpm 11.25.0 and uv 0.12.19, uses immutable dependency locks, the canonical owned PostgreSQL container initializer and installed Chrome pattern, and always removes only labelled owned containers/volumes. The canonical fresh CI source database follows its accepted migration head. The uniquely owned browser database always migrates exactly through accepted `0007_tvt_account_sessions`; these revisions are distinct. No broad foundation/private suite is run.

## Private state and scenario boundary

`WSO_TVT_ACCOUNT_BROWSER_STATE_FILE` is an absolute, unique `auth-state/tvt-account-<run>/context.json` path. The new directory must not exist. Windows inheritance is disabled and the current SID is granted access; the mode-0700 creation also retains privileged OWNER RIGHTS, SYSTEM and Administrators entries. No other ordinary principal is allowed. Linux uses mode 0700. Files are private and bounded to 65,536 bytes. No session, CSRF, database URL, saved key or context JSON is printed. The caller must never upload the context, auth-state folder, traces, videos, logs or request captures.

The state includes `proofKind: actual-pg-rpc-https`, `baseURL`, `tenantId`, real Playwright `cookies`, `csrfToken`, `expiresAt`, synthetic `account` inputs, `expectedProfile`, `controlFile` and `sequence`. Internal TLS file paths and API origin are coordinator-only. WSO sessions are created by the real protected `PostgresSessionStore.create` with a fixed 600-second lifetime and a provisioned synthetic STAFF principal. No in-memory authentication store, generic 401 reauthentication, TTL rewriting or restoration of revoked sessions exists.

Between independent, settled scenarios the driver may exclusively write `{ "op": "session", "sequence": previous + 1 }` to the private control path and poll the state until the sequence changes. The operation rejects actor/tenant selection, unknown keys, non-integer/replayed sequences live TVT sessions, active API calls, active worker calls, and unexpired PostgreSQL tickets (including image/check/login with no identity). A private mode-0600 SQLite gate in the protected fixture directory atomically freezes both API and worker admission before reading activity and PostgreSQL authority, and remains frozen through revoke/create. Calls already in flight may leave while frozen; the gate transaction is never held over application work. Refusal does not rotate state. Frozen admission returns temporary service unavailability; it never creates an account result or bypasses authorization. It revokes the preceding WSO session and creates a fresh same-actor session. Consent is persisted normally and is not reset. Every previous account call must be settled and its TVT session logged out first. The initial consent state is pending.

The upstream is the accepted decoded HTTPS fixture. Its protocol-only PNG marker is replaced in this test module by a valid synthetic PNG showing 1234. The browser consumes a standalone image check once, requests a fresh image for login and sends optional image/second code through the real stack. The fixture's email is supported; its exposed phone value does not assert a phone-login acceptance case. Public error/authorization/invalid-input checks must use real requests; `page.route` account response substitution is forbidden.

The current fixture supports the positive account flow and real authorization/invalid-input failures. Wrong-password, unavailable-upstream, alternate-region and deliberately expired-challenge scenarios are not activated or claimed by these browser cases. Component/proxy controls for those public error states are distinct evidence; an eventual browser extension must control the owned upstream/SQL fixture and retain real Next/API responses.
