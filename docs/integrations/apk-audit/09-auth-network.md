# SuperLive Plus 1.18.1: account, network and local-data audit

## Scope and evidence

Static, read-only review of the installed **1.18.1** base APK. `J:` denotes a path under `C:\wso-private\superliveplus\1.18.1-2026-09-27\jadx-full\sources`; `M:` denotes `apktool/AndroidManifest.xml`; `X:` denotes a decoded resource under `apktool/res`. Line numbers refer to this JADX/apktool extraction. UI and Java call sites establish *possible code paths*, not successful authentication, live endpoint behavior, granted permission, or network security of opaque native libraries. No login, packet capture, account mutation, or device setting change was performed. The complete TVT request and JNI inventories are in [02-protocol-api.md](02-protocol-api.md).

## Transport and privacy observations

1. Manifest sets `networkSecurityConfig` to a resource whose base policy permits cleartext. This is an app-wide Android policy, while many observed cloud defaults are HTTPS; it does **not** imply all requests use cleartext. `M:72`; `X:xml/network_security_config.xml:1-4`; `J:com/tvt/other/CustomPath.java:465-472`.
2. `BaseApplication` installs a custom Glide image `OkHttpClient` whose hostname verifier always accepts and whose trust manager does no certificate checks. The observed caller is Glide URL loading; the source does **not** establish that TVT native protocol or Tyco Retrofit use this client. This behavior should not be copied into a web implementation. `J:defpackage/pe1.java:33-85`; `J:com/tvt/base/common/BaseApplication.java:18-24`.
3. The application installs a logging filter that masks many names, passwords and tokens before its TLog callback, but some direct Android logs print the P2P token and Firebase registration token. This establishes sensitive logging *call sites*, not that logs were collected from this phone. `J:com/tvt/launch/LaunchApplication.java:174-190,432-436`; `J:com/tvt/push/fcm/FirebaseConfig.java:35-47`; `J:com/tvt/push/MyFirebaseMessagingService.java:150-158`.
4. Manifest declares Internet, microphone, camera, location/Wi-Fi, storage/media, notification, Bluetooth, wake/boot and foreground-service permissions. Some names repeat; presence does not show grant or feature use. `M:3-31,48-55,68-72`. `android:allowBackup="false"` and `android:debuggable="false"` are set. `M:72`. The initial launch flow presents a privacy consent dialog and persists a consent flag before ordinary initialization, with a separate bypass condition in the code. `J:com/tvt/launch/MainActivity.java:115-133,311-332,525-539`.
5. Several third-party callback activities and TVT push components are exported in the manifest. Export status alone does not prove a reachable auth bypass; intents, signature checks and provider callback validation need separate testing. `M:150-170,329-365`.

## Web-service parity gates

| Gate | Why the APK alone is insufficient | Targeted verification |
| --- | --- | --- |
| TVT cloud authentication and token rotation | SDK router exposes inputs, but native code and live server control HTTP exchange, `keychain_token`, P2P token, region/DC migration and renewal. | Authorized test-account request/response capture with secrets redacted; login, forced logout, expiration and region-change cases. |
| Device connection from web | `datoken` plus native NAT/media handshake is Android-specific. | Confirm vendor-supported web SDK/API or build an authorized server-side gateway; test device model/firmware, LAN/P2P/relay and renewal. |
| Provider login | Facebook/Google/WeChat/Vimar providers require separate app registration and redirect/origin configuration. | Verify which buttons are actually enabled for the configured package/region and test callbacks with the user's accounts. |
| Tyco panel integration | Separate REST origin, user/password session, panel token and cookies; no evidence all accounts include Tyco. | Test only on a Tyco-enabled account/panel, including login renewal and cookie expiry. |
| Security and privacy | APK's local AES scheme, cleartext allowance, trust-all Glide client and token logging are implementation facts, not requirements to reproduce. | Design web-side credential storage, HTTPS, session isolation and log redaction independently; verify account data handling. |

**Conclusion:** The APK gives a strong **feature and call map** for account/network design. It does not establish a complete wire protocol, authorization to call TVT cloud from a new origin, a public `TVTOpenSDK` browser distribution, or 100% behavioral parity. The minimum remaining evidence is controlled live tracing of the authenticated paths plus vendor capability/SDK terms and model-specific device tests. No such calls were made in this audit.
