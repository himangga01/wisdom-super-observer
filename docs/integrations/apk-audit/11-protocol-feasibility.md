# Protocol feasibility gate for user-visible web parity

Date: 2026-09-27. Scope: a read-only follow-up to the static SuperLive Plus 1.18.1 APK audit. This is a decision aid for planning **100% of the agreed user-visible behavior**, not a claim that any integration works. No account, device, vendor service, or network endpoint was exercised.

## Evidence notation and conclusion

`J:path:line` means `C:\wso-private\superliveplus\1.18.1-2026-09-27\jadx-full\sources\path:line`; `G:file:line` is a saved Ghidra listing in that private directory. `E64:library@offset` and `E32:library@offset` are ELF dynamic-symbol `st_value` addresses, **not APK byte offsets**. The saved arm64 Ghidra image base is `0x100000`; subtract it from a Ghidra `ADDRESS` to obtain the corresponding E64 value. The binary identities and hashes are in [08-native-abi-jni.md](08-native-abi-jni.md). These are static observations; selected Ghidra output does not expose the complete wire protocol.

**Decision now:** a web product can be planned around an account/control adapter, device-session/media adapter, and separate Tyco/cloud adapters, with a feature-by-feature acceptance matrix. **No transport choice can yet be marked proven for 100% parity.** The internal `/sdk/*` paths are Java dispatch identifiers, the APK's `.so` files are Android/JNI binaries, the public availability/terms of this particular SDK are unverified, and live server/device behavior is absent from this evidence. [02-protocol-api.md](02-protocol-api.md), [00-tvtopensdk-web-check.md](00-tvtopensdk-web-check.md), and [09-auth-network.md](09-auth-network.md) contain the broader inventories.

## False shortcuts that the plan must exclude

1. **Calling `/sdk/*` as REST.** It is an in-process route resolved to request classes and JNI, not evidence of a public HTTP endpoint (`J:com/tvt/protocol_sdk/TVTOpenSDK.java:2797-2809`; `J:com/tvt/protocol_sdk/request/UserLoginRequest.java:60-67`). A direct web `fetch('/sdk/userLogin')` has no established service contract.
2. **Treating every declared JNI method as usable.** The existing full symbol reconciliation found 299 `TVTOpenSDK` native declarations, 31 signatures (25 names) without a conventional export in either ABI, and no saved proof of dynamic registration. The missing names include connection, live/playback stream, record, seek, key-frame and snapshot operations ([08-native-abi-jni.md](08-native-abi-jni.md#loads-and-javajni-reconciliation); declarations `J:com/tvt/protocol_sdk/TVTOpenSDK.java:113-119,237,354-358`). This is **unresolved**, not proof that all such calls fail: instrumented load/call evidence is needed for any selected route.
3. **Using the five `TVTOpenSDK` NAT JNI entries as a gateway.** `natConnectDevice`, `natDisConnectDevice`, `natOpenLiveVideo`, `natCloseLiveVideo`, and `natLiveAudioSwitch` have zero-return bodies in both packaged ABIs: E64 `libProtoSDK.so@0x280004,0x28000c,0x280014,0x28001c,0x280024`; E32 `@0x1c3d85,0x1c3d89,0x1c3d8d,0x1c3d91,0x1c3d95`. Arm64 selected decompilation confirms the returns (`G:ghidra-paths.txt:190-223`; `G:ghidra-proto-more.txt:330-353`; [08-native-abi-jni.md](08-native-abi-jni.md#confirmed-stubs-and-body-coverage)). These entries cannot provide live transport in this build. The separately packaged `NetClientProtocal` and `NatTraveral` paths still require proof.
4. **Using `tokenLogin` as a shortcut.** Its excess `libProtoSDK.so` export has no Java declaration and is a bare return (`E64:@0x272aa0`, `E32:@0x1bc069`; `G:ghidra-proto-more.txt:354-361`). It supplies no demonstrated token-login contract.
5. **Equating route presence with feature success.** `/sdk/getDeviceLocalStorageStatus` is registered twice and the later HDD-alarm registration replaces the storage-status request; `CheckImgVerifyCodeRequest.execute` and `VASSetInstSwitchRequest.execute` are empty; two cloud callback bodies are empty ([02-protocol-api.md](02-protocol-api.md#specific-gaps-and-interpretation), and source lines cited there). The acceptance matrix must trace the **actual UI path** and a successful outcome, not count routes.

**Selection rule:** prefer a vendor-supported path if its capability/terms and pilot pass. A gateway or independent implementation is a candidate only after its own proof. Do not select a path on endpoint strings, Java declarations, symbol names, or a single successful login. Multiple paths may be required for Tyco, cloud, WebView/third-party authorization and device media.

## Exact decision gate and proof tests

Before committing to a date or claiming 100% user-visible parity, freeze an **in-scope matrix of every visible action and outcome** from [01](01-ui-feature-inventory.md) through [07](07-ai-cloud-services.md): account registration/recovery/sign-in/out, device onboarding/sharing/configuration, live/playback/export, PTZ/talk/audio, push/alarms, AI/search, cloud, Tyco, purchase/entitlement and relevant external web flows. For each row record supported account type, region, device model/firmware, role/entitlement, transport path, success result, errors, and browser-visible acceptance evidence. A route that is unreachable, stubbed or never returns is a failed row unless a **different proven app-equivalent path** supplies the behavior.

The protocol option is **GO** only when all of the following are true for the agreed matrix:

1. **Right to operate:** vendor terms or other authorization cover the exact account/service access, binaries or protocol use, hosting, distribution and test/deployment environment. An ambiguous SDK download page is not enough.
2. **End-to-end account and session proof:** with an authorized disposable account, capture redacted request/response metadata and app/gateway events for login, challenge/2FA, failure, logout, forced invalidation, token expiry/renewal, app restart and region/DC migration. Show which credentials/tokens cross each boundary, their lifetimes and the correct error handling. Keep actual secrets out of evidence files.
3. **Device and network proof:** on a representative allowed device set, show account list → device-access token → connection → callback/task ID → first decoded live frame and audio, playback search/seek, PTZ command and stop, talkback, and disconnect/cleanup. Repeat across LAN, P2P and relay where the product supports them; test an unreachable/offline device and token expiry midstream. Record model, firmware and entitlement with redacted identifiers.
4. **Other service proof:** separately demonstrate alarm/push delivery, cloud token refresh and encrypted media, Tyco login/cookie/panel state, and any third-party/WebView/paid feature included in the matrix. The [09](09-auth-network.md#web-service-parity-gates) gates describe why these cannot be inferred from the TVT call map.
5. **Browser delivery proof:** demonstrate authenticated multi-user isolation, browser-supported video/audio/microphone behavior, reconnect/background handling, latency and resource limits, and control results/errors on supported browsers. Compare visible states and outcomes with the APK, including permission denied and offline cases.

Each proof test must save a sanitized trace with timestamps/correlation IDs, expected and actual UI outcome, device/firmware/browser/build, transport selected, and a pass/fail verdict. Use a dedicated authorized test account/device; perform state-changing controls only under the test protocol. **NO-GO for a 100% claim** if any required row lacks a permitted integration path or an end-to-end passing test. Record the failing row and seek a scoped requirement change or a different authorized integration; do not silently count a UI mock or a native symbol as parity. The current APK audit is below this gate: it has no live trace, official SDK entitlement, complete native wire semantics, or browser proof.
