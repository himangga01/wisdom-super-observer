# SuperLive Plus 1.18.1: alarms, events and push (static APK audit)

## Scope and evidence key

This is an APK-only audit of the installed 1.18.1 base APK. `J:` means a path under `C:\wso-private\superliveplus\1.18.1-2026-09-27\jadx-full\sources`; `M:` means a line in `apktool/AndroidManifest.xml`; `N64:` means the arm64 `libProtoSDK.so` JNI symbol offset recorded in [02-protocol-api.md](02-protocol-api.md). Line numbers belong to this JADX build. A request class, native export, notification builder or UI control proves code presence, not successful cloud delivery, device support, Android permission grant, or real-time latency. No account, device or service traffic was generated.

The main TVT SDK has **32 routed alarm/event/push request classes** (including seven get-alarm-switch spellings), all of which have Java dispatch and a matching conventional `libProtoSDK.so` export as inventoried in [02-protocol-api.md](02-protocol-api.md). The separate Tyco panel REST interface has **eight relevant route/method declarations** listed below. There are **two identified inbound alarm paths**, FCM and an app-managed TVT push socket. Device login/status callbacks are a separate mechanism and do not establish alarm delivery over the device connection. `J:com/tvt/protocol_sdk/TVTRequesterImpl_Group_sdk.java:320-545`; `J:com/tvt/push/MyFirebaseMessagingService.java:114-145`; `J:com/tvt/push/tvt/PushMessageSocket.java:97-175`; `J:com/tvt/network/MainViewActivity.java:328-344`.

## Inbound transport, registration and lifecycle

1. **FCM**: Manifest registers `MyFirebaseMessagingService` for `MESSAGING_EVENT` and declares Android 13 `POST_NOTIFICATIONS`; `M:13,166-170`. `LaunchApplication` requests an FCM token at startup; `FirebaseConfig` saves it in `FirebaseConfig/LocalFirebaseToken.txt` shared preferences; `J:com/tvt/launch/LaunchApplication.java:709`; `J:com/tvt/push/fcm/FirebaseConfig.java:21-48,67-76`. `onMessageReceived` branches on data `msg_data`: missing data becomes a Tyco `PUSH_ALARM_SYSTEM_MESSAGE`, doorbell invite/ac-video-talk data is converted to a Push2 alarm and may start a ringing notification, and other data is locally broadcast as `receive_message`; it then calls `FcmMessageTransform.transform()` for registered listeners. `J:com/tvt/push/MyFirebaseMessagingService.java:33-99,114-145`; `J:com/tvt/push/fcm/FcmMessageTransform.java:20-48`. No server receipt or Android delivery guarantee is inferable.
2. **FCM token-refresh caveat**: `onNewToken` saves the token and calls platform `sendBroadcast(intent,"refresh_token")`, while `ThirdPushMessageReceiver.c` registers with **LocalBroadcastManager** for `refresh_token`; these are different broadcast domains. The constructed intent has no action, and the receiver also rejects null actions; this specific broadcast cannot reach that registered receiver as written. Other token registration paths remain separate. `J:com/tvt/push/MyFirebaseMessagingService.java:153-163`; `J:com/tvt/push/ThirdPushMessageReceiver.java:181-212`; `J:com/tvt/push/j.java:82-90`. Initial FCM token retrieval only saves to preferences in `FirebaseConfig`; the `/sdk/sendNotificationToken` path exists separately. `J:com/tvt/push/fcm/FirebaseConfig.java:35-48`; `J:defpackage/wf2.java:183`.
3. **TVT socket push**: `j.U` initializes `ThirdPushMessageReceiver`, loads saved TPNS server/token state and discovers a TPNS service via SDNS; `j.D` creates `PushMessageSocket` instances, registers an app token, requests offline messages, and connects. A timer checks service liveness, and the socket reconnects after read failures. `J:com/tvt/push/j.java:164-213,311-320,351-373,379-416,615-624`; `J:com/tvt/push/tvt/PushMessageSocket.java:97-201,704-722`. The socket parses framed XML into `PushMessageInfo` alarms and `PushTransMessageInfo`, delivers through callback `j.p/e`, and acknowledges a message ID/type; offline batches have a separate parser. `J:com/tvt/push/tvt/PushMessageSocket.java:121-171,345-379`; `J:com/tvt/push/j.java:487-492,564-570`. `ThirdPushMessageReceiver` also interprets JSON `/message/publish`, `/message/bus/publish`, `/device/event`, `/device/bind`, then falls back to XML `DevAlarm`/`ADMsg`; `J:com/tvt/push/ThirdPushMessageReceiver.java:97-178`. These paths are inbound push, not evidence that the app polls the alarm-list route continuously.
4. **Push type selection**: `com.tvt.push.e.b` selects `fcm` only when Google Play Services is installed/available, otherwise `tvt`; other constants include `hw` and `line`, but `e.d` is empty and `e.e` returns false, so this wrapper does not demonstrate full Huawei registration. Huawei deep-link activity is manifest-declared. `J:com/tvt/push/e.java:7-24`; `J:com/tvt/push/PushMessageHeader.java:777-781`; `M:151-158`. `PushNotifyService` requests a persisted `JobScheduler` period of 60,000 ms and reschedules itself; its `onStartJob` contains no alarm fetch, and Android may adjust the requested period. `NotifyService` creates/cancels a timer but `onStartCommand` does not start a fetch. `J:com/tvt/push/PushNotifyService.java:14-50`; `NotifyService.java:12-70`.
5. **Foreground/background handling**: `i.D` routes new alarms into local storage and listeners, while `i.E` marks offline messages; callbacks call `M0` for newly inserted messages and `h0` for updates. `J:com/tvt/push/i.java:245-320`. Normal notifications are shown when the app is not foreground and the message is eligible; system messages have their own branch. `NotificationUtils.ShowNotification` assigns a notification ID and a `MainViewActivity` pending intent with serialized alarm data; `PUSH_ALARM_SYSTEM_MESSAGE` routes to `PanelMainActivity`. `J:com/tvt/push/PushMessageDataUtil.java:165-244`; `J:com/tvt/push/NotificationUtils.java:116-175`. For doorbell invitations, Android 8+ builds a high-importance call-style channel with answer/hang-up pending intents, 60-second timeout and screen wake; hang-up/delete reaches `PushMessageReceiver`. `J:com/tvt/push/NotificationUtils.java:232-320`; `J:com/tvt/push/PushMessageReceiver.java:15-31`. Manifest permission declaration alone does not show permission granted.

## Message data, UI and routing

`PushMessageHeader` defines **58 legacy `PUSH_ALARM_*` string constants** and **68 `PUSH2_ALARM_*` constants** in the inspected declaration block (the latter includes prefixes such as `ai_`, `opr_`, `sys_` and `all`, so these are *not* 68 disjoint event outcomes). Representative classes include motion/PIR/sensor, line crossing/perimeter/face/plate and other AI, disk/network/offline anomalies, arm/defense changes, doorbell talk/tamper/open-door, and system/expired messages. Mapping from subtype to localized title/body is explicit in `PushMessageHeader.getAlarmFormatMsg`; `J:com/tvt/push/PushMessageHeader.java:45-112,117-200,1100-1260`. These strings are a **client taxonomy**, not a server or device capability enumeration.

The message screen has separate alarm and system tabs. The alarm tab is populated from the persisted local list, with read/delete actions and an optional Push2 detail request; the system tab fetches `GetServiceMsgList` and sets server status. `J:com/tvt/push/PushMessageActivity.java:280-295,350-381,780-790,955-999,1454-1463,1867-1881,2056-2068`; `J:defpackage/fc3.java:61-68,112-127`. `PushMessageDataUtil.g` checks a deleted-ID blocklist, device identity, message ID duplicates, recency order and a 100-message cap; it persists `LocalPushMessage.txt` per user and reloads on initialization. Doorbell result changes may update an existing ID instead of inserting a second row. `J:com/tvt/push/PushMessageDataUtil.java:165-249,299-341,504-595`; `J:defpackage/ib3.java:36-140`. `PushMessageDataUtil.n()` is **not decompiled** in this JADX build (`:434-501`), so its precise write mechanics remain unresolved despite the visible read path and calls to `m()`.

Alarm detail can show image, face/plate data and doorbell result, and has live/playback/manual-alarm/delete actions. Live/manual alarm routes through `MainViewActivity` with `pushMsgId` and `pushMsgType` (`LP`/`MA`). Playback resolves the device and channels, derives the start time from the alarm timestamp minus the configured lead-in, and opens `PlaybackActivity`; a camera/channel may be absent or offline. `J:com/tvt/push/PushMessageActivity.java:1466-1600,1874-1932,2078-2087,2175-2225,2255-2300,2584-2601`; `J:com/tvt/push/PushMessageHeader.java:189-195`. Notifications use the same `MainViewActivity` alarm-data extra for tap handling (`NotificationUtils.java:124-141`); the actual media session is outside this report and is separately covered in [03-media.md](03-media.md).

The configuration UI exposes per-device Push1/Push2/IPC choices and channel/event selection. `PushConfigMainActivity` builds a device list and opens detail activities according to device type; `Push2ConfigDetailActivity` reads/edits event lists with `sys_`, `ai_`, `smd`, motion and schedule/channel selection; `BindIPCPush2ConfigDetailActivity` edits bound IPC Push2 events. The doorbell-specific screen exposes main push plus invite, open-door, offline, person, motion/PIR, VFD and scene-change switches. The corresponding server routes are the Push1/Push2 configuration routes above. `J:com/tvt/pushconfig/PushConfigMainActivity.java:119-155,339-408,670-750,905-945`; `PushConfigDetailActivity.java:1135-1235`; `Push2ConfigDetailActivity.java:257-290,427-470,883-937,1814-1845`; `BindIPCPush2ConfigDetailActivity.java:810-830`; `IpcPushConfigActivity.java:123-245`; `J:com/tvt/devicemanager/doorbell/DoorBellPushActivity.java:165-267,288-388`; `M:231-234,264`. UI presence is conditional on device capability, brand and notification permission; static sources cannot fix the exact options a specific account sees. `J:defpackage/ef2.java:199-219,488-517`; `J:com/tvt/network/MainViewActivity.java:1058-1061`.

## Separate Tyco panel alarm/notification plane

`defpackage/ki.java` declares `GET rest_api/{apiVersion}/alarms` (:496), `/events` (:531), `/troubles` (:535), `/push_options?token=` (:482), `GET` and `POST /notifications/email` (:491-493,550-552), `POST /update_push_token` (:554-555), and `POST /register_push_recipient` (:561-563): **eight method declarations**. They use panel/session-token handling shown by Retrofit annotations, and must not be conflated with `/sdk` routes. `AlarmFragment` invokes `AlarmViewModel.getAlarms` on screen load (`J:com/tvt/tyco/ui/fragment/alarm/AlarmFragment.java:200-232`; `AlarmViewModel.java:461-475`). `HomeFragment` registers for FCM transform events and refreshes its view on dispatch, also starting/stopping a timer on resume/pause (`J:com/tvt/tyco/ui/fragment/home/HomeFragment.java:210-265`). That is a refresh trigger, not evidence of FCM payload rendering directly into the alarm list.

There is also a **Tyco home-screen polling path**. `HomeFragment.onResume/onPause` starts/stops `PanelHomeViewModel.startTimer`; the partially recovered coroutine shows a 3,000 ms delay followed by panel status/info, troubles, alarms and panel-events fetches in a loop. JADX emits `UnsupportedOperationException` for the full `invokeSuspend` reconstruction, so the 3-second interval and exact loop behavior are evidence from its instruction dump, not a fully reliable Java method body. `J:com/tvt/tyco/ui/fragment/home/HomeFragment.java:251-265`; `PanelHomeViewModel.java:480-569,1270-1288`. This polling is distinct from TVT socket/FCM push and from the declared `/sdk/getDeviceAlarmListPage` request.

Tyco `NotificationViewModel` exposes five filter flags: Alarms `2`, Restore Events `4`, Arm/disarm Events `8`, Notice Events `1024`, Duress Events `1`. It reads push options and posts a `RegisterNotificationRequest(token,"ANDROID",mode,"en_US",7)` using the stored FCM token; `TaskViewModel.updatePushToken` posts `UpdatePushTokenRequest`. `J:com/tvt/tyco/ui/fragment/notification/NotificationViewModel.java:35-43,238-242,348-360,413-447`; `J:com/tvt/tyco/base/TaskViewModel.java:174-214,548-557`; `J:com/tvt/tyco/data/request/{RegisterNotificationRequest,UpdatePushTokenRequest}.java:14-45`. The actual REST host, auth result and push delivery remain unverified.

## Native/device callback boundary and gaps

- `TVTOpenSDK` declares `registerDevStatusNotify()` at `J:com/tvt/protocol_sdk/TVTOpenSDK.java:528`, but neither packaged `libProtoSDK.so` ABI has a conventional export for it. No Java call to this declaration was found in the scoped SDK/network search. Treat this as unresolved, not an operative alarm callback. The UI's `fu3` device login/server-update callbacks (`J:com/tvt/network/MainViewActivity.java:328-344`) are connection-status events, not alarm-message receipt.
- The 32 SDK alarm/push route names and JNI exports establish an ABI boundary only. Native reply JSON and endpoint acceptance are opaque; six specialized get-switch spellings reply with the generic route. The HDD alarm/storage route collision is a concrete reachability issue. `J:com/tvt/protocol_sdk/TVTOpenSDK.java:1125-1131,1666,1749`; `J:com/tvt/protocol_sdk/TVTRequesterImpl_Group_sdk.java:321,545`.
- A source search of application call sites outside `com.tvt.protocol_sdk` found no direct use of the four `/sdk/getDeviceAlarm*` list/latest/count/unread constants. The visible push-message screen instead reads its local cache and Push2 history, while the Tyco panel uses its own REST alarm route. This limits claims about whether the generic SDK alarm-list routes are reached by this UI version. `J:com/tvt/push/PushMessageActivity.java:780-790`; `J:com/tvt/push/i.java:208-218`; `J:com/tvt/tyco/ui/fragment/alarm/AlarmViewModel.java:461-475`.
- `PushMessageDataUtil.n()` failed JADX decompilation; `PushMessageDataUtil.g` is visible, but persistence and error behavior cannot be completely reconstructed. `J:com/tvt/push/PushMessageDataUtil.java:434-501`. Push2 event payload conversion also depends on obfuscated `com.tvt.push.c` and server data, so type coverage and attachment URLs are inferred from fields/UI, not validated responses. `J:com/tvt/push/i.java:165-177,208-218`; `J:com/tvt/push/PushMessageActivity.java:980-989`.
- The FCM refresh broadcast mismatch, conditional Play Services fallback, Android notification permission, foreground state and device membership can each alter delivery/display. The socket's offline catch-up (`PUSH_GET_OFFLINE_MSG`) and Push2 history fetch (`lastId`/`lastTime`) are distinct from live push; no static proof of lossless dedup across them or of event latency exists. `J:com/tvt/push/MyFirebaseMessagingService.java:153-163`; `J:com/tvt/push/ThirdPushMessageReceiver.java:181-212`; `J:com/tvt/push/j.java:186-203`; `J:defpackage/da3.java:331-381`.
- No device/account runtime test was made. Server schemas, pagination ordering, notification tap behavior on each Android version, settings persistence on each camera type, and alarm-to-video success remain gaps for a separately authorized dynamic test. Static presence should not be represented as feature parity.
