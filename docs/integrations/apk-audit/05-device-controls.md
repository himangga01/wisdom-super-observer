# SuperLive Plus 1.18.1 — device controls and configuration (static APK audit)

Audited 2026-09-27 from the already extracted APK at `C:\wso-private\superliveplus\1.18.1-2026-09-27`. This is a **static call-path map**, not a claim that any camera, recorder, account service, or relay accepted a command. No login, device command, configuration change, or service implementation was run. Values that could identify a device, account, network, or credential are intentionally omitted.

`J:path:line` means a line in `jadx-full/sources/`; `R:path:line` means a line in `apktool/res/`; `M:line` means `apktool/AndroidManifest.xml`. A bare `:line` immediately after a `J:` citation refers to that same Java file. `E:library:symbol` means a JNI export confirmed by the ABI comparison in [02-protocol-api.md](02-protocol-api.md), not a decompiled implementation. `[read]` retrieves state, `[write]` can change a device/account/relay, `[local]` changes only app settings or local device list, and `[display]` is a rendering interaction. Every result remains **runtime unverified**. Capability, login state, model, firmware, brand flag, and permission checks can hide or reject a path.

The recorder/IPC path is not the account `/sdk/*` path. `ew3` (NVMS account) sends XML-like requests with `NetClientProtocal.RequestApiTransport` and stores task observers, `J:defpackage/ew3.java:4602-4603,4622-4668`; `J:com/tvt/network/NetClientProtocal.java:219,372-375`. ## Device administration, channels, and remote/local settings

`DeviceInfoActivity` is a capability-gated hub: it routes common info, channel info, power, diagnosis, doorbell chime/time, and upgrade screens and directly toggles some device features, `J:com/tvt/devicemanager/DeviceInfoActivity.java:350-381,435-599,1017-1080,1442-1462,1715-1772`. `DeviceCommonInfoActivity` presents basic, recording, alarm, network, disk, and online-user data; query IDs and view selection are at `J:com/tvt/device/ui/information/DeviceCommonInfoActivity.java:342-397,451-494`. This is chiefly `[read]`, not a full editor for each category. `DeviceChannelInfoActivity` parses motion/intelligent/online/name/record status, `J:com/tvt/device/ui/information/DeviceChannelInfoActivity.java:45,247-252,261-319`; `[read]`. Channel rename is separately exposed as account route `/sdk/DeviceChlReName`, `J:com/tvt/protocol_sdk/TVTOpenSDK.java:139` and [02](02-protocol-api.md#devices-groups-and-configuration); `[write]`. Sharing permission and channel assignment live in the separate share screens, not this status list.

The direct recorder configuration inventory visible in `cw3`/`ew3` includes basic/time, channel list and status, encode, recording status/distribution, alarm state, net status/ports, storage/disk details, channel video parameters/AZ, fisheye capability, P2P and wiper capability. Representative `[read]` dispatches: `J:defpackage/cw3.java:601,620,652,714,833,898,1022,1050,2054-2058,2602-2603`; `J:defpackage/ew3.java:864,946,1007,1078,1220,1309,1487,1612,5032`. Direct `[write]` examples: video/lens edits above; wiper on/off via `ptzMoveCall` `J:defpackage/cw3.java:3908,6937`; manual unlocking `J:defpackage/ew3.java:5359`; cloud upgrade node `:5396`; device alarm/PIR/line/perimeter toggles from `DeviceInfoActivity`, `J:com/tvt/devicemanager/DeviceInfoActivity.java:267-337,465-599`. Protocol names are Java constants and request construction, not complete validated wire specifications.

Remote settings deserves separate treatment. `/home/RemoteWebActivity` captures JS prompts, queues command/parameter requests, and dispatches each to connected `fu3.D0(url,message)`, then returns replies to JS, `J:com/tvt/config/ui/RemoteWebActivity.java:385-423,798-868,872-888`; the page loads into WebView at `:1132-1150`. Since the UI command set is page-driven, a Java-only inventory cannot enumerate every recorder setting or assert safe read-only behavior. Its bridge accepts both read and device-changing operations. Local settings instead toggles `GlobalUnit` values for auto-connect, video resolution/adaptation/OSD, PTZ direction/gesture, snapshot/record retention, rotation, caching and Wi-Fi/domain display, `J:com/tvt/config/ui/LocalConfigActivity.java:489-711,929-1010,1038-1093,1097-1207`; `R:layout/activity_local_config.xml`. These are `[local]` preference writes except navigation into the Wi-Fi flow.

Account SDK device administration is a separate route family. The implemented request-class → `TVTOpenSDK` JNI surface includes device list/detail/ability/online reads, bind/register/transfer/unbind, rename/remark/group membership/order, alarm/motion/offline switches, arm/wake/sleep, net-safe switch, local-storage status/format, and reboot; route-by-route input and callback classifications are in [02-protocol-api.md](02-protocol-api.md#devices-groups-and-configuration). Key device-changing JNI declarations/exports are `J:com/tvt/protocol_sdk/TVTOpenSDK.java:137-185,620-640` and `E:libProtoSDK.so:deviceBind/deviceUnBind/deviceReboot/deviceSetMotionSwitch/setOnOffDeviceConfig` (both ABIs per [02](02-protocol-api.md#native-declaration-and-jni-export-inventory)). The Java route may modify cloud account binding rather than recorder firmware; do not infer one from the other. `LocalDeviceActivity` has local add/login and delete/share branches, `J:com/tvt/devicemanager/LocalDeviceActivity.java:1945-2001,2093-2164,2348-2390,2425-2451`; deleting a local list entry and `/sdk/deviceUnBind` are distinct effects and need runtime distinction.

## Coverage, gaps, and safe interpretation

This audit covers the principal UI routes, direct NVMS/DVR3/IPC session calls, the account `/sdk/*` route inventory, Wi-Fi provisioning, and the Tyco panel output branch. It cross-checks UI resources against Java callers and uses the existing ABI export table for selected `TVTOpenSDK` methods. It does **not** claim exhaustive behavior of remotely loaded configuration pages, every obfuscated `fu3` subtype, every native function body, or every possible device capability. The baseline reports seven DEX files, 19,116 decompiled Java files, and 391 JADX errors; see [00-coverage-baseline.md](00-coverage-baseline.md). Some unrelated Tyco coroutine bodies fail decompilation, though the on/off request coroutine above is recovered. Static route or JNI presence is lower confidence than a decoded native body; neither is a successful runtime test.

Specific unresolved checks for an authorized future device test: which device models expose PTZ/presets/fisheye and which command mapping they use; whether movement stops reliably on touch-up and which errors reach Java; whether image edits persist and round-trip; whether WebView remote settings command pages are bundled or updated; whether local deletion also unbinds an account; whether Wi-Fi provisioning and upgrade recover after interruption; and whether Tyco timed output state represents actual relay state. These are open questions, not implied successes.
