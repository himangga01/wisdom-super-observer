# SuperLive Plus 1.18.1 — AI, Tyco, cloud and optional services

## Scope and evidence standard

This is a **static audit of the installed base APK**. `J:` denotes a line in `C:\wso-private\superliveplus\1.18.1-2026-09-27\jadx-full\sources`; `R:` denotes an `apktool/res` resource; `E:` denotes a JNI name found in the packaged ELF symbol text. The line numbers refer to this JADX run. The baseline is seven DEX files, 19,116 Java outputs, 2,187 under `com/tvt`, and 391 JADX errors; see [00-coverage-baseline.md](00-coverage-baseline.md). No account, camera, panel, purchase, traffic or server response was used. A screen, request declaration or native export is **presence evidence**, not proof that a service accepts it. Media transport and alarm delivery are covered by [03-media.md](03-media.md) and [04-alarms-push.md](04-alarms-push.md).

I indexed all Java files in the eight relevant `com/tvt` trees: `ai` **106**, legacy `search` **25**, `tyco` **218**, `cloudstorage` **105**, `valueaddedservice` **35**, `file_sdk` **15**, `filemanager` **12**, and `web` **4** (**520**, including generated route injectors and models). I also inspected the obfuscated `fu3`/`cw3`/`ew3` device-session implementations, `ki` Tyco Retrofit interface, SDK route map and native declarations. The count is a package-file count, not 520 working features. Twelve `/ai/*` Activity routes, five `/share/*` VAS Activity routes and 35 Tyco REST method declarations were found; `J:com/tvt/ai/search/AISearchInputActivity.java:92`, `AIAttributeSearchActivity.java:48`, `AIPicSearchListActivity.java:45`; `J:com/tvt/valueaddedservice/ValueAddedServiceActivity.java:34`, `VASServiceDetailActivity.java:57`; `J:defpackage/ki.java:470-602`.

### Face and plate enrollment, and local detection

The face capture flow starts `FaceRecognitionActivity`, which dispatches either `AddFaceActivity` or legacy search; `J:com/tvt/search/FaceRecognitionActivity.java:33-48`; live UI invokes it in `J:defpackage/dj2.java:346-354`. `AddFaceActivity` hands a selected image path to its view, asks the connected device for a face group list (`fu3.A0`), and checks device capability/state; `J:com/tvt/search/AddFaceActivity.java:72-110`; `J:defpackage/cw3.java:3397-3399`. The view's submit path collects identity/group fields and image bytes, checks the device connection, then calls `fu3.l`; `J:defpackage/ac.java:558-590`. `cw3` and `ew3` serialize that to `createFacePersonnalInfo` (APK spelling), with base64 image, dimensions, group/property and optional validity times; `J:defpackage/cw3.java:6684-6685`; `J:defpackage/ew3.java:7254-7255`; `J:com/tvt/configure/NVMS/HTTP_PROTOCOL_TYPE.java:56`. This is a **device enrollment write** carrying personal and face-image data. The camera view **does run local OpenCV face detection** from the packaged YuNet ONNX and LBP cascade resources before handing a bitmap/path onward; `J:com/tvt/search/view/d.java:106-119,140-169,302-313`; `J:com/tvt/search/view/FaceRecognitionViewLayout.java:238-267,335-338`; `R:raw/face_detection_yunet_2023mar.onnx` and `R:raw/lbpcascade_frontalface.xml`. This local detection supports capture/quality control; it does not prove local face recognition or search. Actual enrollment success and biometric handling on the recorder remain untested.

Plate registration is a separate device write: `AddLicensePlateActivity` requires a connected supported device, calls `u1` to add a library, `w4` to list libraries and `v1` to add a plate with owner/phone/vehicle fields; `J:com/tvt/search/AddLicensePlateActivity.java:30-70`; `J:defpackage/dj2.java:489-491`. `cw3` maps these to `ADD_PLATE_LIBRARY`, `QUERY_PLATE_LIBRARY` and `ADD_PLATE_NUMBER` XML commands; `J:defpackage/cw3.java:7719-7721,8000-8002,8089-8091`. The account-session implementation has corresponding methods (`J:defpackage/ew3.java:7708,7904,7965`). These are device-side registration/configuration, not an account cloud face database established by this APK.

## File SDK and cloud service boundary

`FileSyncSDK` loads `ProtoSDK`, declares create/init/quit, cloud-to-local, local-to-cloud, compare, delete and stop JNI operations, and maps type values 4096–4099 to those calls; `J:com/tvt/file_sdk/FileSyncSDK.java:20-43,115-127`. On completion it invokes success/error callbacks and maps 11 error enum values (0–10), including decrypt, HTTP, upload, delete and other-device-login errors; `J:com/tvt/file_sdk/FileSyncSDK.java:45-76`; `J:com/tvt/file_sdk/bean/FileSyncSDKErrorCode.java:36-51`. The app calls `FileSyncSDK.Init()` at startup, but a search of `com/tvt` and top-level `defpackage` found **no constructor/start call site outside this class**; `J:com/tvt/launch/LaunchApplication.java:600`. Its public surface is therefore packaged and initialized, while an app UI sync workflow is not established. The JNI name text for all eight declared `FileSyncSDK` methods is present in both `libProtoSDK.so` ABIs; this is an export-string check, not native body validation.

The file manager is a different feature: `FileManagerActivity` and `SearchFileActivity` manage/search app files (`J:com/tvt/filemanager/FileManagerActivity.java:33`; `J:com/tvt/filemanager/SearchFileActivity.java:43`) and the side menu exposes it (`J:defpackage/ef2.java:486,518-519`). It should not be treated as a proven FileSyncSDK cloud browser. Cloud video download is separately traced in [03-media.md](03-media.md).

## Limits affecting a feature-equivalence claim

- The 391 JADX errors include the AI sequential task coroutine and two legacy search view methods (`jadx-full.log:4894-4896`), six Tyco coroutine bodies (`:4921-4926`, including the nested output callback), plus generated `R.*` constructors. These are the nine non-`R.*` `com.tvt` method errors in the baseline. The AI task scheduler is visible but its failed `startExecution` suspend body cannot establish cancellation/fairness behavior; `J:com/tvt/ai/search/task/SequentialTaskManager.java:87-162`. Other app code can carry warnings even without a logged method error.
- `HttpRequestUtils` provides a generic JSON POST implementation with 30-second timeouts (`J:com/tvt/ai/search/utils/HttpRequestUtils.java:49-82,165-173`), but the traced AI search models above use recorder sessions and the translation SDK. Its existence does not establish a separate public AI HTTP endpoint.
- The route and JNI maps establish call boundaries; they do not validate server schemas, model support, payment eligibility, cloud object availability, encryption/decryption, export success, face/plate enrollment, Tyco task completion, or page content. These require separately authorized runtime evidence. Static UI/code/JNI coverage is recorded here; **device/account/paid-service behavior remains unverified**.
