# SuperLive Plus 1.18.1 — audio, talk, and audible alarm static audit

## Scope, evidence, and coverage

This audit uses the preserved 1.18.1 APK output at `C:\wso-private\superliveplus\1.18.1-2026-09-27`: seven-DEX JADX source, Apktool manifest/resources, both bundled ARM ABIs' ELF dynamic symbols, and saved Ghidra output. It is a **static** account of reachable-looking code and native boundaries. No microphone, phone, device, account, network session, alarm, or file upload was exercised. A positive JNI export establishes a callable entry, not successful runtime audio. The initial APK identity/tool baseline is in [the static report](../superlive-static-analysis.md).

Evidence labels are `J:relative/path.java:line` under `jadx-full/sources`, `E:library.so:JNI-method@0xELF-offset` for arm64 `.dynsym` values unless stated, and `G:ghidra-file.txt:method@0xELF-offset` for saved decompilation. The saved Ghidra listing adds `0x100000` to these ELF values. Line ranges are source line numbers, not APK offsets. The account classes are obfuscated; their identifiers do not establish protocol names by themselves. JADX reports 391 method errors across 19,116 Java outputs, and some audio methods carry duplicated-block warnings. Exact wire packet format, codec negotiation outcomes, acoustic output, and firmware behavior require runtime/native evidence.

The audit screened the `com/tvt/live`, `video`, `playback`, `network`, `devicemanager`, `doorbell`, `ai/search`, `speechrecognitionsdk`, and `com/sdk/mediacodec` Java paths, then followed account overrides in `defpackage` (`ku3`, `ew3`, `iu3`, `cw3`, `nu3`, and shared `fu3`). It compared relevant JNI declarations against arm64 and armv7 exports of `libNetClientProtocal.so`, `libH264Decode.so`, and `libAudioCodec.so`, and reviewed the saved `libNetClientProtocal.so`/`libProtoSDK.so` Ghidra bodies. The installed library inventory is 13 arm64 and 12 armv7 `.so` files; this is a feature-path review, not full native decompilation of every library. `J:com/tvt/network/NetClientProtocal.java:254-264,331-333,384-387`; `J:com/sdk/mediacodec/AudioCodec.java:12-59`; `J:com/sdk/mediacodec/H264Decode.java:611-612,738-767`.

## Receive audio: live listening, playback, and phone output

`com.tvt.live.a` maintains one active listen target. Selecting a different channel ends the prior listen state; starting listen calls `LiveTalkManager.D()` to stop talk first. `fu3.b5` leads, in the primary IPC account `ku3`, to `NetClientProtocal.OpenLiveAudio` or `CloseLiveAudio` with the existing live task ID; close also resets local decoding state. NVMS and doorbell account implementations have corresponding switches. `J:com/tvt/live/a.java:124-165`; `J:defpackage/ku3.java:6512-6539`; `J:defpackage/ew3.java:6341-6366`; `J:defpackage/iu3.java:4458-4483`. Saved native bodies call `Net_Client_Protocal_Open_LiveAudio` and `Net_Client_Protocal_Close_LiveAudio` respectively. `G:ghidra-net-paths.txt:OpenLiveAudio@0x11e400,CloseLiveAudio@0x11e41c`.

Native task callbacks are mapped to observers by task ID in `NetClientProtocal`. In `ku3`, incoming audio header `x41` sets codec/sample-rate metadata, packet type 6 reaches `onAudioData`, and type 8 is used for decoded talk-return output. `VideoView` packages audio bytes, channel, timestamps, encoding and sample rate into `AudioPacket`; `GL2JNIView` sends it to `H264Decode.NewPlayerPushAudioPacket`. `J:com/tvt/network/NetClientProtocal.java:159-180`; `J:defpackage/ku3.java:1070-1104,2290-2325,2339-2415`; `J:com/tvt/video/VideoView.java:2431-2452,2491-2503`; `J:com/tvt/video/GL2JNIView.java:615-618`; `J:com/tvt/network/AudioPacket.java:4-11`; `J:com/sdk/mediacodec/H264Decode.java:326,611-612`; `E:libH264Decode.so:NewPlayerPushAudioPacket@0x127084`. The native player-audio body and actual speaker playback were not established by the saved decompilation.

Playback has an explicit UI boolean `bOpenAudio` and a `RequestPlaybackStream` path that carries account audio state. The app source search found no invocation of `NetClientProtocal.OpenPlaybackAudio` or `ClosePlaybackAudio` beyond their declarations, although **both** are present as JNI exports. Thus those two entries are capabilities in this binary, not proven playback UI call edges. `J:com/tvt/playback/view/PlaybackViewLayout.java:4314-4340,4902-4914`; `J:defpackage/ku3.java:5600-5669`; `J:com/tvt/network/NetClientProtocal.java:271,333`; `E:libNetClientProtocal.so:OpenPlaybackAudio@0x11e438,ClosePlaybackAudio@0x11e454`. The ELF symbol table and Ghidra names put live audio at `0x11e400`/`0x11e41c` and playback audio at `0x11e438`/`0x11e454`; the [media report](03-media.md) now uses the same mapping.

Talk sessions may also return device audio to the **phone**: `fu3` creates a `zl` `AudioTrack`, and account callbacks write decoded bytes to it. `J:defpackage/fu3.java:740-754,1886-1904`; `J:defpackage/zl.java:68-106,122-195`; `J:defpackage/iu3.java:3790-3845`. This Android output is separate from the remote device's `loudSpeaker` setting and from the live `AudioPacket` player path.

## Talk/send: UI → capture → codec → network task

The live Talk button resolves the selected tile and whether the device/channel form is supported, then checks online status, channel sound capability, device permission, and `RECORD_AUDIO`. `LiveTalkManager` allows one active talk session, stops live listening before beginning, calls account `t5`, and reflects callbacks/errors in the UI. `J:com/tvt/live/view/LiveOperateBarView.java:324-332`; `J:defpackage/lb4.java:304-361,418-465`; `J:com/tvt/live/LiveTalkManager.java:133-175,203-235,250-273,382-406`.

The common `fu3` capture loop initializes Android `AudioRecord` as mono PCM16 at 8 kHz, or 16 kHz for server type 5, with microphone source chosen around headset/acoustic-echo conditions. It creates available `AcousticEchoCanceler`, `AutomaticGainControl`, and `NoiseSuppressor` effects, reads samples (640-byte blocks for some types), converts `short[]` where needed, and calls `u5(bytes,length,V1,W1)` while talk is active. Stop clears its flag, releases `AudioRecord` and effects, and can pause/clear the local return `AudioTrack`. `J:defpackage/fu3.java:488-490,512-630,676-686,902-950,1219-1234,1261-1263`. The Java path includes a conditional debug PCM file writer under a debug flag; the audit did not exercise it. `J:defpackage/fu3.java:537-545,572-580`.

For `ku3`/`ew3`/`iu3`, `t5(true,...)` creates a `RequestLiveTalkBack` task and retains its positive ID. Stop releases recorder/codec state and calls `JniCloseLiveTalkBack` for that ID. `ku3` and `ew3` require 640-byte source chunks and use negotiated codec fields with `H264Decode.g711Encode[Ex]` or `AudioCodec` G.711 variants before `SendLiveTalkBackData`; a conditional channel UID is forwarded. The doorbell `iu3` branch explicitly G.711 A-encodes and sends audio type 1. `J:defpackage/ku3.java:8087-8126,8226-8344`; `J:defpackage/ew3.java:7660-7699,7750-7867`; `J:defpackage/iu3.java:6855-6885,6951-6975`; `J:com/sdk/mediacodec/H264Decode.java:738-767`; `J:com/sdk/mediacodec/AudioCodec.java:27-59,63-112`. Decompiled `ku3`/`ew3` branches contain duplicated-code warnings, so the exact codec/audio-type mapping for every negotiated mode should be treated as unresolved.

The saved native `RequestLiveTalkBack` body forwards to `Net_Client_Protocal_RequestLiveTalkBack`, and close forwards to its matching native close. The `SendLiveTalkBackData` JNI body gets the Java byte array, allocates `length + 1`, copies the requested bytes, converts an optional UID string, invokes `Net_Client_Protocal_SendLiveTalkBackData`, then frees the buffer. That proves the Java-to-native byte handoff; the lower native function's wire framing, transport, security, and remote playback are outside the saved body. The decompiler renders the request function's return inconsistently with Java's integer declaration, so the Java task-ID behavior is the safe statement. `J:com/tvt/network/NetClientProtocal.java:100,223,261-264,384-387,404`; `G:ghidra-net-paths.txt:RequestLiveTalkBack@0x11e4c8,JniCloseLiveTalkBack@0x11e4f0,SendLiveTalkBackData@0x11e50c`.

There are **additional legacy account socket implementations**: `cw3` builds talk start/stop messages, encodes G.711/ADPCM, frames payload headers and sends through its account socket; `nu3` similarly sends start/stop frames and encoded `AudioCodec` blocks. Their packet constructors and `m5` send calls are distinct from the `NetClientProtocal` JNI task path. They must be included when assessing supported device families; the full wire layouts were not independently decoded. `J:defpackage/cw3.java:7591-7645,7753-7881`; `J:defpackage/nu3.java:4044-4069,4107-4139`; receive switches at `J:defpackage/cw3.java:5562-5590` and `J:defpackage/nu3.java:3012-3038`. `fu3.t5`'s base implementation only stops common state, so the five observed account overrides are the useful transport inventory. `J:defpackage/fu3.java:2120-2125`.

## Doorbell call lifecycle

A ring push/intent can route to `DoorbellVideoTalkActivity` with the device serial and out-of-app-call state. The activity requests microphone permission, shows answer/hangup/mute/open-door controls, imposes approximately 30/60-second timers, and starts live video separately. On answer, it starts `iu3.t5(true,false,0)` and sends XML `DoorbellVideoTalk`/`Connect` with a GUID. On hangup/reject or pause cleanup, it closes listening/talk and sends `Bye` or `Reject`. Mute calls `iu3.G5`. `J:com/tvt/network/MainViewActivity.java:1178-1194,1252,1329`; `J:com/tvt/devicemanager/doorbell/DoorbellVideoTalkActivity.java:61-85,170-218,416-425,469-509,539-544,593-634,693-703,730-756`; `J:com/tvt/devicemanager/doorbell/DoorBellView.java:170-252`; `J:defpackage/iu3.java:2234-2239`.

The activity's own `ov3.onAudioData` methods are empty; the account object handles returned talk audio and its `AudioTrack`. Thus an empty activity callback is not evidence that intercom audio is absent. Task errors close/report through `iu3`; an in-call lifecycle interruption can terminate the session. This sequence is a **doorbell-specific handshake plus the shared talkback media task**, not a confirmed SIP/telephony or separate broadcast stack. `J:com/tvt/devicemanager/doorbell/DoorbellVideoTalkActivity.java:636-642,730-756`; `J:defpackage/iu3.java:3790-3845,4930-4950,6872-6885`.

## Prerecorded leave-word and audible alarm controls

`DeviceInfoActivity` queries `GetLeaveWordAudioConfig`, parses `<leaveWordAudio>` enable/selected `audioID` and an `<audioList>` of IDs/names. The leave-word screen chooses one supplied ID and sends `SetLeaveWordAudioConfig` XML (`switch`, `audioID`). Its audio callbacks are empty, and this path has no file picker or microphone capture. The selection is best described as device-provided prerecorded leave-word configuration. The clip asset format, where it resides, playback trigger, and firmware result remain unknown. `J:com/tvt/devicemanager/DeviceInfoActivity.java:381,1172,2977-3005`; `J:com/tvt/devicemanager/doorbell/leavewordaudio/LeaveWordAudioActivity.java:58-80,209-303`; `J:defpackage/iu3.java:2248-2254,5229-5230`.

Audible alarm is more capable: capability indicators include `SupportManualAudioAlarm` and `supportAudioAlarmOut`, and menu/control visibility depends on support flags. The popup can request alarm settings, toggle the switch, audition an existing item, rename/delete it, or pick an `audio/*` file. The picker path validates RIFF/WAVE PCM and 8 kHz sample rate, Base64-encodes bytes, and submits an add-customize-audio-alarm command with size/channel checks; account variants implement analogous XML/socket commands. This is a stored clip/control path that may drive a **device speaker**, subject to device capability and firmware response. It is not the phone microphone stream and does not establish generic public-address broadcasting. `J:defpackage/qz0.java:29`; `J:defpackage/pz0.java:29`; `J:defpackage/dl.java:185-255,642-760,795-843`; `J:defpackage/pv4.java:29-79`; `J:defpackage/ku3.java:4425-4430,4814-4816,5378-5383,6001-6005,7932-7933,8004-8020`; `J:defpackage/nu3.java:3961-3976`; `J:defpackage/cw3.java:7500-7510`.

`g7`'s `TALKBACK`/`ALARM_AUDIO` choice refers to device audio input/output and loudspeaker configuration. The live Talk workflow may switch from `ALARM_AUDIO` to `TALKBACK` first. This supports a speaker-mode distinction, but there is no evidence that the two settings create two independent live audio transports. `J:defpackage/g7.java:69-310`; `J:defpackage/lb4.java:530-558`; `J:com/tvt/live/LiveTalkManager.java:296-309,417-455`.

## Speech recognition and the meaning of “broadcast”

AI search hides speech input unless Android resolves a `RecognitionService`. Its wrapper checks/request `RECORD_AUDIO` and optional Bluetooth permission, constructs a `SpeechRecognizer` `RECOGNIZE_SPEECH` intent with locale/partial-result settings, and returns text to the search field. The default setup passes `onDevice=false`; a `prefer offline` extra is set only for an on-device request. This does **not** prove whether the installed Android speech provider sends audio to a remote service or stores it locally. No `NetClientProtocal`/talk JNI call edge was found from this search path. `J:com/tvt/ai/search/AISearchInputActivity.java:693-710,1519-1600,1633-1744`; `J:com/tvt/speechrecognitionsdk/SpeechRecognitionService.java:339-382,442-579,717-789`.

The Java name/path search for `broadcastaudio`, `audiobroadcast`, `audio.broadcast`, `broadcast.audio`, `voicebroadcast`, `broadcastvoice`, and `publicaddress` across app and obfuscated sources found **no distinct audible broadcast entry point**. A `MulticastSocket.setBroadcast(true)` call belongs to LAN discovery, not speech or speaker transmission. `J:defpackage/zv3.java:90-100`. The supported static claim is narrower than a universal absence: this APK exposes live Talk/intercom, device speaker mode, and audible alarm clips, while **no separately named broadcast audio UI → account → JNI path was found**. Obfuscated or firmware-only behavior and unexamined native interior could still use another term.

`TVTOpenSDK.natLiveAudioSwitch` is exported but its saved `libProtoSDK.so` body returns zero; its `playbackAudioSwitch`/`realPlayAudioSwitch` declarations lack conventional matching JNI exports in the 13-arm64-library name screen. These cannot replace the active `NetClientProtocal` evidence. `J:com/tvt/protocol_sdk/TVTOpenSDK.java:499,518-524,2620-2624`; `G:ghidra-proto-more.txt:natLiveAudioSwitch@0x280024`; [protocol audit](02-protocol-api.md).
