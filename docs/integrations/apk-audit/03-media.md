# SuperLive Plus 1.18.1 — media static audit

## Scope and evidence

This is a static audit of the preserved APK, JADX output, Apktool resources, arm64 ELF files and existing Ghidra output in `C:\wso-private\superliveplus\1.18.1-2026-09-27`. It does not establish that any device, account, stream, file transfer or codec path works at runtime. The APK identity and tool versions are recorded in [the initial static report](../superlive-static-analysis.md). No device or account data was used here.

Evidence labels below use `J:relative/path.java:line` for `jadx-full/sources`, `E:lib.so:symbol@0xoffset` for an exported ELF64 `.dynsym` value, and `G:file.txt:symbol@0xoffset` for previously saved Ghidra decompilation. The Ghidra listing displays addresses with `0x100000` added to the ELF value. Offsets apply only to this APK's arm64 libraries. An `E` label proves that a JNI entry is exported; it does **not** prove its body or a successful runtime operation.

Coverage method: indexed all **208** Java files in the app's `live` (41), `playback` (13), `video` (5), `network` (28), `backup` (4), `cloudstorage` (105), and `filemanager` (12) trees; searched the **281** `protocol_sdk/request` files and relevant obfuscated `defpackage` account classes; then manually traced the call sites named below. Examined the Java native declarations and dynamic symbols of the media libraries, and screened method-name bytes across **all 13** bundled arm64 `.so` files. Reviewed available Ghidra bodies for `libNetClientProtocal.so`, `libH264Decode.so`, and the relevant `libProtoSDK.so` stubs. This is a feature-path audit, not a proof that every branch of the 208 files decompiled correctly. JADX reports **391** method errors overall, mainly in bundled framework/Kotlin code; some app methods carry type-inference or duplicated-code warnings. The original APK has seven DEX files. `J:com/tvt/video/VideoView.java:2800-2803` is one visible warning immediately before an otherwise readable frame method.

## Unresolved and likely inactive surfaces

* A name screen of `TVTOpenSDK.java` found **292 distinct native method names**, **38** with live/playback/record/snapshot/download/audio/key-frame wording. Only **17 of those 38** have the exact method name as a NUL-terminated byte string in any of the 13 arm64 libraries. The other **21** include `openRealPlayStream`, `openPlaybackStream`, `closeRealPlayStream`, `closePlaybackStream`, `seekPlaybackStream`, device/playback recording searches, playback audio switches, key-frame commands and `sendCmdToSnapShot`. No direct matching `Java_*` export was found for these names. This does not categorically rule out indirect registration, code loading or an unused compatibility declaration, but it forbids treating these Java declarations or `/sdk/*` routes as a confirmed working media path. The active call sites above favor `NetClientProtocal`. `J:com/tvt/protocol_sdk/TVTOpenSDK.java:113-117,293-297,354-358,510-524,574-604,2643-2649`; `J:com/tvt/protocol_sdk/Protocol_Type.java:163-164`.
* `TVTOpenSDK.natOpenLiveVideo`, `natCloseLiveVideo`, and `natLiveAudioSwitch` have exported entries, but the saved Ghidra bodies return zero immediately, as does `natConnectDevice`. They are **stubs in this binary**, despite their names. `G:ghidra-paths.txt:natConnectDevice@0x280004,natOpenLiveVideo@0x280014,natCloseLiveVideo@0x28001c`; `G:ghidra-proto-more.txt:natLiveAudioSwitch@0x280024`.
* `NetClientProtocal.SnapLivePictureTask` is exported and registers an auto-destroy observer, but a searched app-wide call-site scan found only its wrapper declaration/implementation. Visible capture goes through the local decoder/view path. `J:com/tvt/network/NetClientProtocal.java:426-431`; `J:com/tvt/video/GL2JNIView.java:375,394`.
* The saved Ghidra media analysis decompiled four decoder functions and the primary live/open/close audio JNI bodies, but **not** device playback, MP4 writer, snapshot or cloud player bodies. An export plus a Java call is a narrower claim than a fully mapped native implementation. JADX's 391 errors and obfuscated account/parser classes also limit assurance that every media branch was recovered.

## Runtime questions for an authorized device test

1. Which device types select IPC, NVMS or doorbell account code, and what channel/index/stream IDs appear at each callback? Are close/error observers and native tasks released during rapid multiview switching and reconnect?
2. Which live and playback codecs and audio formats arrive, and when does Android hardware decoding fall back to software? What are frame ordering, timebase, key-frame, audio-sync and backpressure behavior?
3. Which device playback modes support date/log search, reverse/key-frame seeking, audio, snapshots and local recording? What do channel values above 1000 represent in actual callbacks?
4. Do local snapshots and MP4 recordings produce valid files on current Android storage APIs, and where are they visible/exportable? Does low-storage cleanup preserve existing user files?
5. Does cloud OSS token refresh/decryption, cloud playback and the one-active-task cloud download path complete, resume, cancel and clean up correctly? What exactly is saved to local storage and shareable?

These questions are pending runtime verification; none are inferred as successful from static declarations or UI labels.
