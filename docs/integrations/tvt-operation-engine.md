# Protected operation engine

Analysis and implementation date: 2026-10-02. Source baseline: `b17df332c046b48cb884829e17bf5826c731596e`, plus the root-accepted W05 account-session implementation. This is an internal engine. It provides no public operations API, vendor writer, payment checkout, firmware transfer, Tyco transport, or authoritative upstream reader. `MATCHED=0`; `release_ready=false`.

## Admission and intent

`OperationService` accepts a typed payment, firmware, Tyco action, or delete intent. Actor and tenant are absent from the request models. PostgreSQL derives them from the protected transaction context. Job execution derives them from the persisted job and its current lease generation. Caller GUCs, an OWNER role, a store assignment, and knowledge of an identity ID confer no domain authority.

Migration `0008_tvt_operation_engine` adds write action admission without changing the existing read authorization function. Admission intersects current membership, identity grant, active device/channel/store or Tyco panel, store assignment, upstream observation, capability observation, connection generation, lifecycle, and expiration. A trusted exact-target observation is also required. Its deterministic intent key binds the firmware version, payment product/term/quote, Tyco target/requested state, or delete target. Runtime roles cannot create these observations. The migration seeds no positive authority; tests create clearly synthetic facts in owned databases. A future reviewed backend must populate observations from actual upstream evidence.

The SQL canonicalizer independently validates the typed shape, rejects extra fields, normalizes UUID spelling, and computes the hold key. Actor, idempotency key, store selection, and browser discriminators cannot change the business key. Store permission remains part of the payload and authorization decision. Python provides corresponding typed intent semantics; persisted digests are generated by SQL and are not interchangeable with Python's diagnostic digests.

## Confirmation, durability, and reconciliation

`prepare` reserves `(tenant, actor, idempotency_key)` and an exclusive `(tenant, canonical business intent)` hold atomically. Concurrent actors cannot reserve the same business intent. A matching actor key returns the existing operation without reissuing its secret confirmation. A changed authorized payload conflicts. The confirmation lasts five minutes. Reading or preparing an expired unsubmitted draft, or cancelling it, marks it failed and deletes only its own hold.

`submit` checks the original actor, role, key, payload, confirmation digest, current facts, and expiration. It commits the operation transition, T05 job, outbox, and dispatcher projection in the caller's transaction. The internal operation UUID is the T05 idempotency key. Callers must commit before dispatch; no bridge call occurs in this transaction.

After submission, unresolved outcomes retain the hold indefinitely. Cancellation, missing handlers, job failure, exhausted execution, or revoked authorization during execution resolve conservatively to `UNKNOWN_OUTCOME`. Connection callback failure records uncertainty in a separate fenced transaction. If that transaction cannot reach PostgreSQL, the existing durable unresolved hold remains, and the T05 watchdog completes the uncertainty transition when the database is available. Revocation is checked on each boundary; a revoked job not revisited by a worker remains held until the dispatcher/watchdog processes it.

`reconcile` requests another backend readback attempt using the same job and outbox. It never accepts an outcome from a public caller. It refreshes currently authorized facts, increments the job fence, and marks the attempt as reconciliation so it cannot automatically retry an external write. Only a worker's typed `AuthoritativeReadback`, published under the current lease token and generation with fresh domain checks, releases the hold and records definitive success or failure. No reader or successful evidence is invented in this slice. Readback reference values must be opaque local labels, not URLs or credentials.

## T05 and T04 composition

`compose_registry(base)` retains every supplied job definition and rejects name collisions. The fixed additions are `TVT_ACCOUNT_OPERATION/TENANT`, `TVT_DEVICE_OPERATION/STORE`, and `TYCO_OPERATION/TENANT`. All are external writes with one execution attempt and explicit credential requirements. The process entrypoints use this composed registry for both dispatch and workers. Standalone constructors must receive the same registry explicitly. The current baseline has `IMPORT` and `REGISTRATION`; no production `ASSET_RETENTION` definition exists. A composition test proves that a supplied retention definition is preserved. Implementing retention remains its owning task's work.

Generic enqueue rejects domain kinds. Restrictive job visibility blocks OWNER access to another actor's operation, and cancellation rejects false authorization. Claim, step, generic credential issue, and readback publication cannot bypass domain checks. The existing six-field broker reference, outbox, inbox, lease generation, and watchdog remain the sole job lifecycle.

`OperationCredentialStore` uses T04's `SecretCipher` and existing encrypted connection bytes. Tickets are bound to the operation, job generation, current facts, connection generation, version, and a short expiry. Redemption consumes a ticket in its own committed transaction. Every callback use revalidates before decryption and again before returning. Callback results are never exposed; callback errors are redacted. Failure marks the still-matching job uncertain. Managed W05 USER tokens additionally require a ready session and idle renewal; P2P/device/challenge tokens and the generic managed-token handle path remain unavailable. Feature transports must supply their own bounded I/O and authoritative readback implementation.

## Migration and verification

New private tables use forced RLS and a non-login, non-superuser owner. Runtime roles have function-only admission. Existing function bodies are saved privately, replaced with exact checked patches while preserving public owners/ACLs/settings, and restored on downgrade. Existing action constraints are backed up and restored exactly. Downgrade with newly admitted write observation rows may require an explicit data migration before the original read-only constraints can be restored; no automatic deletion of those facts is performed.

The owned PostgreSQL 17 development suite exercises migration up/down/re-up, original rows and owners, function definitions and ACLs, RLS policies, constraints, cross-actor concurrency, actor idempotency, expiration, canonicalization, exact-target denial, protected-context bypass attempts, atomic job/outbox submission, revoked read/cancel/claim/step, uncertainty, lost leases, definitive success/failure readback, managed credential redemption/use, callback result refusal, and payment/Tyco target restrictions. It uses a unique database name/OID/owner/comment cleanup guard and does not reset, provision, restart, or write the shared source database.

Run unit tests normally with `python -m pytest tests/tvt_parity/test_operations.py`. The integration module skips unless `WSO_TEST_W02_OPERATION_DIAGNOSTIC=1` and all explicitly configured development role URLs are supplied. Windows PostgreSQL diagnostics are not Linux/Celery/broker, private-asset, device, SDK, or parity acceptance. Detailed source manifests, causal failures, successful captures, and cleanup receipts are in the W02 operation report under the implementation plan's `.superpowers/sdd` directory.
