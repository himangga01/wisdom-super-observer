## Common request and response contract

Internal `/sdk/...` names select Java requests; they are not HTTP URLs. The ordinary account operations below reach `ProtoSdkManager::addHttpTask`, then the previously decoded POST JSON transport. Use the configured, allowlisted region/brand origin with `Content-Type: application/json;charset=UTF-8`. Do not let a public command choose an origin. Native bootstrap defaults and persisted DC state are configuration context, not unrestricted redirect authority.

The generic basic envelope is `basic = {ver:"1.0", id:string, time:integer, nonce:integer}` plus the current account `token` when present. `id` is the decimal task ID string; `time` is Unix seconds; `nonce` is native numeric nonce output. Registration, final recovery and provider login/bind-after-login-required construct their own **1.1** basic envelope, described below; they must not inherit a logged-in token accidentally. Generic authenticated security commands use the **USER account token**, never the P2P token or device-access token. Native `createBasicJson` is `N:0x2d057c`, `createPostJson` is `N:0x2cc3f0`; T and the W04 transport follow-up give the member and method mapping.

Native callback JSON uses `basic.msgcode` as its business result and `data` as operation data, with a message normalized for Java's `q63`/`vm3` wrappers. `J:defpackage/q63.java:40–77` extracts those members. HTTP status must remain independent. The service adapter should call an operation successful only for HTTP 2xx and business 200; dynamic-image states are distinct results, not successful account creation. Unknown additional data remains private and bounded.

The object-data callback branch invokes `getIdCodeFromJson`, `getRSAPublicKeyFromJson`, `getAESEncryptKeyFromJson` and `getTokenFromJson` (T `native-callback.txt:1050–1178`). These are **native side effects before Java discards or reclassifies a dynamic reply**. A nonempty account `data.token` and P2P `data.p2pId`, or `tid` fallback, are separate values. A key or token field's existence in this generic parser does not prove every endpoint returns it or permit the service to authenticate a failed operation.

Native business 404 is also used for DC relocation. Preserve the existing bounded, allowlisted, pending-candidate handling; never treat business 404 as an HTTP redirect or silently retry a registration/removal write. Static serializers do not define server idempotency, code consumption or a safe replay policy. Prelogin challenge/key state must be bound to the initiating actor/browser flow, region, brand, account and purpose. Changing that scope invalidates the locally held state.

Preserve the source difference in UI parity tests; it is not evidence of distinct server CAPTCHA lengths.

## Account-existence contract

`CheckAccountIsRegisterRequest.CheckAccountRegister(account,type)` stores the two constructor fields but **reorders** them when calling `RequestCallback.checkAccountIsRegister(callbackId,type,account)` (`J:com/tvt/protocol_sdk/request/CheckAccountIsRegisterRequest.java:14–34`; `RequestCallback.java:58`). `TVTOpenSDK.java:105,909–914` adds the SDK handle and routes the reply through `checkAccountIsRegisterReply` to the original callback. JNI `N:0x3837cc` reads account from its last Java argument, retains the integer type, and invokes vtable offset `0x28` as `(account,type,callback)` (E:32–63); V:22–31 identifies the target as `N:0x326f50`. `a62.c` exposes this SDK/model operation; the inspected registration verification screen's `n(AccountRegisterResp)` callback is empty (`RegisterVerifyCodeActivity.java:575–577`). This source path does not establish that an existence check is a mandatory registration precursor.

| Supported web account mode | HTTP request | Operation data |
| --- | --- | --- |
| **1: phone** | POST `/user/info/phone/is-exist` | `mobile:string` containing the nonempty account argument; `customerAppId:string` only when SDK configuration is nonempty |
| **2: email** | POST `/user/info/email/is-exist` | `email:string` containing the nonempty account argument; `customerAppId:string` only when SDK configuration is nonempty |

Both use ordinary `addHttpTask` and the common **1.0 generic basic envelope**: decimal task ID string, time/nonce integers and current **USER token only when present**. This native operation does not require a token or strip one from an already logged-in manager. The proposed prelogin adapter uses its isolated prelogin state and therefore supplies no USER, P2P or device token. It uses the existing allowlisted region/brand origin and POST JSON transport. No `loginName`, `account`, `loginType`, dynamic/image code, language, customerMark, password, sign, RSA or AES field is emitted by this operation. `accountType` selects the path/key locally; it is not a data member. Evidence: U:1209–1570, especially guards at 1279–1282, app condition at 1288–1324, email at 1326–1380, phone at 1382–1436 and task dispatch at 1519; I:2527–2556 resolves both paths and account keys.

Native guards require nonempty account plus manager and callback; a failed guard returns zero without HTTP dispatch or an explicit synthetic business-error callback. It does **not** reject other integers at entry. For a type other than 1 or 2, the initialized phone path remains selected, neither account field/data object is constructed, and an **empty operation-payload string** reaches generic task dispatch (U:1438–1444,1476–1519). Although customerAppId may already have been collected internally, that invalid-mode branch does not wrap the field list into request data. Reject unsupported modes before dispatch as **web validation policy**; do not model the native fallback as a valid phone request or claim native range rejection.

The expected successful operation data is an object with **`isExist:boolean`**: true means registered and false means not registered (`J:com/tvt/login/model/bean/AccountRegisterResp.java:8–12,42–47`). `a62.a` parses the generic reply via `q63.b(message,AccountRegisterResp.class)` and forwards the model, without a required-field or null check, to `b62.onSuccess`; ordinary failure forwards only error code/message to `b62.a` (`a62.java:46–84`). The shared parser reads generic code/basic.msgcode, normalizes network/transport failures, takes `data` with an `array` fallback, and attempts Gson parsing. Absent/empty data, JSON null or a caught parse failure can leave the model null; there is no operation-specific guarantee that code 200 has a usable model (`q63.java:41–74,143–157`; `vm3.java:7–20`). Neither the wrapper nor the boolean model establishes presence validation for `isExist`.

The common dispatcher chooses success from business code 200 rather than model validity. It forwards ordinary non-success results to `onFailed`; the specific auth/account codes **7000,7003,10002,11101,7004,7009,7088,7089,7090** instead emit global event 65634 and skip that local failure callback. A null wrapper or reactive error invokes failure -100; a disposed emitter drops delivery (`bm3.java:18–40,57–62`; `qo3.java:12–33`; `vm3.java:19–20`). These are APK callback semantics, not permission to report “not registered” after an error. The web adapter must require HTTP 2xx, business 200 and an explicitly present JSON boolean `isExist`; missing/null/malformed/wrong-type data becomes a fixed protocol failure, while auth/network/business failures retain their typed failure state. That stricter shape check is adapter policy. No token/session creation, registration write or server existence response was executed here.

A true 200 explicitly sets bean data to null, causing the presenter to begin the resend countdown. The reachable model uses the generic business-15 request. Implementing the legacy route as if it sent registration SMS would fabricate behavior.

No decoded code gives challenge TTL, one-use semantics, maximum attempts, or a token binding the returned `idCode` to a particular form. Locally bind and expire flows under explicit service policy, preserve the upstream expiry/error result, and label the local timeout as policy rather than an APK-derived server constant. A received response can replace challenge state; do not reuse a stale challenge after changing account/purpose/region. No irreversible request should be retried automatically after an unknown transport outcome.

There is **no clear `dynamicCode` data member**, no `imgCode`/`idCode` member and no login-style UUID proof in this registration serializer. The verification code is incorporated in `basic.sign`. No token is constructed in this custom basic object. Invalid required native inputs trigger callback business **1011** and return task ID 0; an absent RSA key triggers callback **1016**, null data and no HTTP dispatch (R:166–178,270–322,982–1037). If RSA encryption returns less than one, the helper follows its empty-result path (C:504–541). **PEM parse failure is different:** after `PEM_read_bio_RSA_PUBKEY` returns null, the decompile passes a null char pointer into a string-constructor thunk (C:480–490). The retained evidence does not resolve whether that constructor safely returns an empty string, throws or fails otherwise; no crash is asserted. The registration caller does not independently reject an empty returned ciphertext before enqueue. The web adapter should validate SPKI/RSA and reject malformed or missing key material before sending, reporting a fixed safe protocol error without reproducing unresolved native failure behavior.

### Runtime key provenance and representation

There is no dedicated key-acquisition endpoint proven by this source pass. The source-proven producer is `HttpsRequestTask::getRSAPublicKeyFromJson` at **`N:0x2d268c`**, which reads **`publicKey` from the response data object**, then calls `ProtoSdkManager::setRsaPublicKey` at `N:0x2d86b0`. Its only discovered code caller is the generic object-data callback (`N:0x2ce324`; V:1–11). The setter stores a wrapped key in manager memory at offset `0x100`; registration obtains it with `getRsaPublicKey` at `N:0x2d88d0`. This is a runtime-supplied key, not an embedded registration RSA key.

The reachable registration precursor is `/user/sms-code/no-token/get` with business 15; image fetch may also pass through the same callback. Their request schemas are established above. The generic callback can install `data.publicKey` from either response when present. **Static client code cannot prove which deployed response actually contains it, that every 200 includes it, its lifetime, or that two challenge responses use the same key.** The smallest acceptance step is a sanitized response-field observation of that already decoded precursor, not guessing a `/rsa/key` URL. A concrete backend can already ingest a validated key from its own admitted precursor response and require it before registration; it must expose a missing-key state rather than invent or embed one.

`encryTool::getRSAPublickey` at `N:0x2d87c0` wraps the supplied text in `BEGIN PUBLIC KEY` / `END PUBLIC KEY` markers and inserts line breaks at approximately 64-character intervals. Therefore the expected input is the **Base64 body of DER SubjectPublicKeyInfo**, not a private key, raw DER bytes, or a PKCS#1 `RSA PUBLIC KEY` object. It does not strip existing PEM markers; accepting arbitrary complete PEM as the server member is not source-equivalent. `PEM_read_bio_RSA_PUBKEY` parses the wrapper.

`RSAEncryptByPublickey` at **`N:0x348308`** obtains the modulus byte length using `RSA_size`, allocates that amount, and calls **`RSA_public_encrypt(..., padding=1)`** exactly once. This establishes PKCS#1 v1.5 encryption, not OAEP, and **no block splitting**. The plaintext is always a 32-byte MD5 hex string in registration; the generic primitive would reject overlength data through OpenSSL. There is no explicit modulus-size, exponent, certificate/pin, key-ID, expiry or signature check at this wrapper. A deployment key size is unknown. `Base64EncodeToStr` at `N:0x2dee60` sets BIO flag `0x100`, producing ordinary Base64 without line breaks (F:256–300). Randomized padding means ciphertext is not a fixed hash vector.

The key is as trustworthy as the selected response channel and its validation. Keep the existing allowlisted verified HTTPS transport; the native key parser supplies no separate proof of authenticity. Associate key admission with the exact response flow and region; never let a browser supply a replacement encryption key or return the upstream key/ciphertext in logs.

JNI obtains text through `GetStringUTFChars` (JNI offset `0x548`), which is modified UTF-8. ASCII and non-NUL BMP strings, including the Korean example below, coincide with ordinary UTF-8. Supplementary characters and NUL require an explicit compatibility decision; the proposed initial adapter should reject those rather than claim that ordinary Python UTF-8 matches every Java string. Digest helpers return lowercase hex; R and T resolve the input ordering and case.

One source quirk must remain visible: **registration calls `setMd5Password(MD5(dynamicCode))`**, while its encrypted data password and signature are derived from the actual password (R:183–193). JNI and the vtable confirm no hidden argument swap. This is temporary native crypto state used by later AES-key processing, not evidence that a web session should persist an MD5 of the code or accept registration as authenticated login. Test it as an observed APK side effect; do not silently change the wire formula to make the setter name appear consistent.

### Registration result and next UI state

Java parses the generic callback as a string payload and forwards errors; no registration-specific success token schema is required by its presenter (`a62.java:531–565`). On success `xr4.java:42–46` remembers the account/mode/country label, then the verification activity reports success and routes to the appropriate login screen, sets `BaseActivity.needClearPwd=true`, emits event 65636 and finishes (`RegisterVerifyCodeActivity.java:535–538,617–631`). It does **not** set `isLogin=true`. Any generic native token fields still require separate analysis/acceptance before web-session creation. The readback proving usable registration is a subsequent authorized login/profile read, which was not executed.

Password-update crypto is a third, distinct rule. `N:0x34857c` normalizes plaintext to Base64 when it does not already end in `=`; the MD5 string is therefore Base64-encoded, then the low-level AES helper decodes it back. Session key text ending in `=` is Base64-decoded, otherwise used as raw bytes. Only **16,24,32-byte** key lengths pass. `N:0x3176e8` encrypts independent 16-byte blocks (`AES_encrypt`), hence **ECB**; it zero-pads only an incomplete block and adds no extra block for aligned input. MD5 hex is exactly 32 bytes and needs no padding. Output is Base64. This is not AES-CBC/PKCS7 used by unrelated Java local-storage code (S:646–817; A:119–206).

AES-key provenance is also runtime state: the generic response parser reads `sid` and `tokenId`, calls `setAESEncryptKey` (`N:0x2d893c`), and uses the temporary MD5 password (or existing key fallback) to decrypt the supplied key material; it caches the token-ID association and persists the resulting session key through the SDK key-value callback (S:38–645). The helper uses the same trailing-`=` heuristic for input representation. This pass establishes the block rule and key provenance, but **does not have a server fixture proving the exact `sid` byte representation or successful key derivation/rotation for all login families**. Keep password-update composition in a separate scope until a synthetic sid fixture and setter edge cases are independently reviewed. Do not fabricate an AES key from the account token or reuse a browser secret.

Password-update success removes the saved `pwd` value (`uh2.java:123–129`), emits event **65587**, shows success and closes the edit screen (`ModifyPasswordByPhoneActivity.java:487–492`; mail counterpart `:481–486`). `SafeSettingActivity.java:475–481` handles that event by refreshing user information through `k2` → `qp3.d` → `go4.a(false,...)`; it is not the logout callback. Separately, `SafeSettingActivity.java:332–346` clears `keychain_token` on logout and emits event 65560. `BaseActivity.java:498–519,546–550` handles forced logout/blacklist, and `TVTOpenSDK.java:3376–3386` resets DC state when the user-token value is cleared. These local paths do not prove that password update revokes P2P sessions or every other TVT login server-side. In the web service revoke only sessions bound to the affected TVT identity after the appropriate definitive result; retain the independent T03 principal.

## Concrete next implementation scopes and open questions

1. **Prelogin account-flow adapter:** extend the existing private typed protocol/client with dynamic results that preserve original code, an actor/flow-bound runtime `publicKey` admission result, registration serializer, final recovery serializer and account-existence checks. Reuse existing process-contained HTTPS and origin policy. Add a bounded prelogin state machine, the source-specific image loop, configured local rate limits and cancellation. Registration result returns to login; recovery does not mint a session. No new database, vendor SDK distribution, or generic native gateway is required to begin this source-derived scope. Keep RSA-key absence an explicit result; do not make up a key endpoint.
2. **Authenticated security adapter:** bind admission to W02/W05 current USER identity and credentials; add contact bind/change and source-confirmed nickname/type edits with server readback. Separately review AES sid/key derivation fixtures before composing password update. Add an explicitly reviewed account-operation kind and UNKNOWN outcome handling before removal. Avatar multipart and LINE RESTful decodes are targeted next source tasks, not reasons to postpone the proved serializers.
3. **Provider adapter/UI:** implement provider-state and cancellation handling using owned web registration configuration, then decoded third-login/bind/unbind/opaque chain serializers. Independently support Vimar type 7 if configured. Keep web QR declared until an actual entry path is established. Source-presence and synthetic tests cannot promote any provider to runtime acceptance.

Open source/runtime questions are: which challenge response carries `publicKey` in each region/brand and how it rotates; all successful/failed response shapes; exact server challenge/code TTL and consumption; which existing sessions survive password reset/update; sid representation across login families; supplementary-character compatibility; null-field behavior in profile JNI; profile/type permissions and post-write persistence; provider browser-code compatibility; QR validity/expiry; avatar multipart details; LINE raw request schemas; and account-removal device/share consequences. Product decisions include local challenge expiry/rate policy, web provider availability, identity-specific revocation scope and recovery/removal readback UX. Each is separate from the implemented source formulas and the unexecuted acceptance record.
