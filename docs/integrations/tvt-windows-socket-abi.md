# Verified Windows NetSocket raw transport boundary

Analysis date: 2026-10-03 (Asia/Seoul). This is static recovery for an isolated Windows AMD64 helper. Native loading, SN discovery, device authentication and frames have not executed. `MATCHED=0`, release readiness is false. The source baseline is the accepted W04 Windows SDK extraction packet and the new W04 socket ABI brief; no Git baseline was independently read. The APK-derived N9000 codec remains responsible for greeting interpretation and credential/wire authentication.

## Minimum recovered surface

The exact client `NetSocket.dll` is 462848 bytes, SHA-256 `ebcfcadc7763086418c26490774c5ce36688fc6d4d2187dd6aae264e84f8806d`; `NatClientSDK.dll` is 632832 bytes, SHA-256 `f884bb14a1d8b2bf9bd2e79e05c86636d27332859308665423783b6712754510`. Both are AMD64 PE32+. The header is [tvt_socket_verified.h](../../services/tvt-windows-helper/include/tvt_socket_verified.h). It supplies exact decorated lookup identifiers and primitive function pointer types, plus a separately named physical callback view. It neither loads a DLL nor implements a provider.

The usable static path is Initial → SetP2PServerAddr → AddConnectByP2P2 → PopConnectResult → read the cached 64-byte greeting once → RegisterNode → Start → callback receive / Send → Stop → DestroyHNetCommunication → Quit. This is a candidate execution sequence grounded in bodies; its ordering and performance still require an isolated native/device probe. No platform node, channel registry, NetClient login or live-node API is needed for this raw path. A generated socket ID or a transport connect result is not device authentication.

All RVAs below use image base `0x180000000`. Exact decorations are in the header and `byte-vectors.json`; MSVC decoration and wrapper instructions independently support each primitive declaration. Windows x64 uses 8-byte pointers, 4-byte `int`/`unsigned int`/`long`, 2-byte `unsigned short`, and 1-byte `bool`. Calls use the Windows AMD64 register/stack convention despite source decoration saying `__cdecl`.

There is no named NetSocket version export, separate NAT2 socket allocation export, bounded interrupt/cancel export or general synchronous NAT2 receive export. Both `Send_Immediate` overloads and the `Recv_Immediate(...,bool*)` overload check P2P1/native socket maps rather than the NAT2 map. They are excluded from the helper surface. The unrelated asynchronous container interface, full direct NAT generator/notifier interfaces, token/key getters, all platform APIs, and nonnull pair containers remain unavailable for this integration.

## Callback object, data and lifetime

The raw path uses the NetSocket manager's own NAT interfaces: constructor `0xbb30` installs three vptrs at `+0`, `+8`, `+0x10`; the main NAT table at `0x5e290` has six code entries. Its data callback at `0x165d0` holds manager lock `+0x480`, looks up the NAT record, and first caches `min(input length,64-cached)` bytes at record `+0xb0`, tracking count at `+0xf0`. It returns only that consumed count. The lower NAT manager at `0x283c0` snapshots registered notifiers and returns the first positive consumption count; complete lower buffering/retry semantics still require a native capture. Once cache reaches 64 and active is 1, it calls the **caller observer** vtable slot `+8` and returns its EAX consumption count. Null/nonpositive NAT input instead marks record failed and returns zero; it does not notify the caller observer of closure.

The caller dispatch instruction sequence at `0x1679a–0x167dd` passes RCX=observer, EDX=ID bits32, R8=data pointer, R9D=positive length32, stack arg5=qword zero, stack arg6=RegisterNode context. Slot `+8` returns consumed bytes in EAX. It runs while the NetSocket manager lock is held. Copy accepted bytes into a bounded private queue before returning; return only the consumed positive count and perform no blocking work/native reentrant call from this callback. Use a queue cap and a worker deadline. Data pointers are borrowed, not transferable ownership; neither validity after return nor retention permission exists.

Independent compiled caller evidence comes from **NetCommon.dll sequence 19**, SHA-256 `d0c004bf4d8f2dc9955c6e07ab4c3585a60bfd25d7c4a4ab3d8a91a6ab8f5475`. This is analysis input only, not required by NetSocket's import closure. `CSocketDataObserver` base constructor `0x97840` writes only its vptr and returns `this`; destructor body `0x97af0` writes the same base vptr. Base vtable `0x11bd00` has a deleting destructor `0x984f0` at slot0 and purecall at slot1; deleting destructor passes allocation size 8 and uses the low flag bit to decide free. The compiled `CNetProtocolProcECMS` caller passes its observer subobject at object `+0x40` to RegisterNode (`0x98748`). Its observer table `0x11bda0` slot0 adjusts `this` by -0x40 before destruction, slot1 is `0x98790`. That method accepts fifth arg as a nullable pointer to 4-byte output (writes zero if nonnull) and returns input length. Its sixth context argument is unused; the NetSocket call site nevertheless supplies it.

The header's `observer_view` / `observer_vtable_view` deliberately describe the **physical scoped NAT2 dispatch**: 8-byte vptr-only view, two 8-byte slots, explicit `this`, machine-width ID/length/data/null/context arguments. Its fifth pointer is opaque because this branch always passes NULL and source signedness/type naming is not recovered. It is not an asserted complete vendor class declaration. A helper can construct its own physical view and stable table; it must not call internal NetCommon constructors or transplant the full platform object. Root review must assess that interop boundary before executing it. The header exposes the deleting-destructor slot shape to preserve table position; no vendor destructor call on the custom view is supported or needed by the observed raw path.

Start enables delivery; Stop leaves the stored object pointer; UnRegisterNode does not remove it. No proof of all copied NAT dispatches finishing at shutdown exists. Retain the object/table/context through helper process lifetime, keep DLLs mapped, and use process termination/replacement as the outer bounded interrupt. No in-process interrupt function is declared. `Stop`/Destroy/Quit can be used for attempted orderly worker cleanup, but cannot substantiate a quiescence guarantee or safe early DLL unloading.

## Native configuration and write semantics

SetP2PServerAddr initializes NAT with a NULL generator. The first P2P2 connection lazily constructs zeroed `0x148` startup bytes: hostname at `0x00` (63-byte copy), port16 at `0x40`, generated client GUID text at `0x42` (63-byte copy), type32=5 at `0x104`, label `nvms 2.2` at `0x108` (63-byte copy). It registers object+8 with SetNatServerNotifier, object with SetNotifier, then Start, and sets its own started flag regardless of Start's result. It constructs zeroed `0x1004` request bytes with type32=0, uppercase digest text at +4 and calls ConnectDev(request,0,25). Start's wrapper unconditionally returns AL=1; neither that byte nor the manager flag is a NAT operational-success gate. No user-filled startup structure is necessary at this boundary.

NAT2 Send flow: NetSocket `0x12690` → NAT `0x270a0` → `0x39b00` → transport vtable slot `+0x18` → CTNATUdtSocket `0x41900` → `0x4dc70`. `0x4dc70` checks connection/free block capacity, copies both caller spans into an owned temporary, optionally appends container spans, calls `0x4c470`, and frees the temporary before return. `0x4c470` copies into private blocks of at most `0x4d4` (1236) payload bytes before queue insertion. Caller buffers therefore need to remain valid only through the call on this recovered UDT branch, and no observer object is called during the copy path. The non-UDT or future subtype contract is not established.

Observed returns include `-1` for missing/disconnected failures and `0` for no accepted progress, including capacity/backpressure or lower socket lookup failure; other observed returns report the requested total. A critical nuance: `0x4dc70` logs an assertion when `0x4c470` queues fewer bytes than requested but still returns the original total. A positive return is neither reliable delivery proof nor sufficient evidence of full enqueue under races. Serialize helper writes, bound spans/queue/deadlines, and validate actual N9000 protocol responses. Do not fabricate authentication/frame success from enqueue counts.

## Next concrete implementation sequence

1. Root independently reviews the header's primitive aliases, physical observer interop and offset/byte evidence. Keep the helper isolated and retain its callback table/object until process termination; use process deadlines as the interruption boundary.
2. Stage the exact fourteen DLL identities in a private fixed package, resolve imports in the helper only, and record a real load/attach receipt. A failed load must identify its missing/incompatible dependency. Keep transport/auth/frame capabilities unavailable until their respective stages succeed.
3. Exercise Initial/config/connect, poll the actual status, read the greeting into a 64-byte buffer once, create the caller-owned two-slot physical observer, RegisterNode/Start, then drive the existing N9000 codec using callback bytes and serialized bounded Send. The greeting is the first input to the codec; cached bytes are not redelivered via the later callback.
4. Record actual credential handshake and authenticated responses before channel/media commands. Do not use the platform live API with raw channel integers. If vendor send reports success while the peer does not respond, retain that failure rather than manufacturing delivery/authentication.
5. Verify orderly close attempts and process deadline replacement, then separately demonstrate channel enumeration and one decoded frame using supported raw wire/media contracts. Native interrupt, in-process unloading/quiescence, arbitrary transport subtypes and full vendor source interfaces remain explicit unavailable capabilities.

Open product questions: supported device/auth family for this raw codec, bounded receive/queue limits, expected SN input character set/length, measured helper concurrency and stream capacity, and distribution/hosting permissions for the exact private binaries. They do not replace the authorized implementation/probe sequence.
