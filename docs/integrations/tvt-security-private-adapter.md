Source: SuperLive Plus 1.18.1, APK SHA-256 `f57ff98226fcc7a0ec3587b077d5538facb57cc5b713a0938d1ee02b0f72f281`. This is a private Python adapter handoff. **MATCHED=0; release_ready=false.**

## Private interface and lifecycle

Construct `SecurityClient(account: AccountClient, *, protocol: SecurityProtocol | None = None)` in trusted server code. It shares that exact AccountClient, its AccountProtocol task allocator, scope, allowed origin, single in-flight admission, total deadline, verified TLS child, cancellation and quarantine. An optional SecurityProtocol must share the same AccountProtocol instance. `SecurityClient.close()` closes the shared AccountClient. No second process or network manager exists.

Every operation takes `scope: TvtIdentityRef`, `token: PrivateToken`, and keyword-only `deadline_ms: int` (1–60000), `correlation_id: str` (the existing bounded ASCII correlation format). Scope/token checks require the configured identity and USER token family. Direct construction, equality and key-state checks establish consistency only; the protected worker must still admit current credentials and authority before calling.

All input records are frozen dataclasses with hidden representations. Name/type checks are strict; string limits, unsupported NUL/surrogate/non-BMP rejection, signed integer limits, body bounds and task-ID bounds reuse AccountProtocol. The profile's `name` and `address` are mandatory explicit empty strings: this is the approved local representation of constructor-unset JNI values. Nonempty values are rejected so this slice does not introduce additional editable fields.

Every request uses generic `basic` version1.0 with task ID, admitted USER `token`, time and nonce. There is no old-password member, registration RSA, login SHA512 or extra padding block. Seven additions to AccountProtocol.KNOWN_PATHS retain every previous route; the eighth operation's dynamic-code path was already allowed. Profile annotations `userName`, `mobile` and `email` are not emitted. UI account types1/4 never grant web roles.

`CodePurpose` is closed to PASSWORD1, REMOVAL_PREPARATION2, EMAIL3 and PHONE4. `CodeStage` is CURRENT, OLD or NEW. Password/removal preparation use CURRENT with an empty current-account selector. Contact OLD uses an empty current-account selector; contact NEW requires the new account. EMAIL requires login_type2; PHONE requires1. Password/removal accept source phone/email types1/2. Purpose2 prepares a code only; no removal writer is exposed. Code stage is local metadata and is not serialized. The future worker must bind each actual code to identity, stage, account and purpose; supplying a correctly shaped record proves none of those facts.

An image code includes both `idCode` and `imgCode`; empty image code omits both even if an ID was supplied. Nonempty image code without ID fails locally. `SecurityProtocol(account_protocol, customer_app_id="", default_domain="")` accepts server configuration; optional `customerAppId` and lowercase MD5(default-domain UTF-8) `customerMark` follow the source presence branches. There is no arbitrary URL argument.

## Results and uncertainty

`SecurityResult[T]` retains bounded numeric HTTP/business status, correlation, closed `AccountErrorCode`, private typed value and private pending DC hint. States are ACKNOWLEDGED, READ, CODE_SENT, IMAGE_REQUIRED, IMAGE_REJECTED, REJECTED and UNKNOWN_OUTCOME. `ok` requires HTTP2xx/business200, no error, and an acknowledged/read/code-sent state. IMAGE_REQUIRED1007 and IMAGE_REJECTED1005 retain their business code and never become successful writes.

`Acknowledgement` discards the raw acknowledgement payload, including any vendor strings, tokens or sid. It proves only a successful status acknowledgement. `LoginTypes.entries` is a tuple of private `LoginType(user_id, login_name, login_type)` records. Explicit `[]` proves a reported empty inventory; absent/null/malformed data, missing/wrongly typed members, duplicate rows, over64 rows or over4096-byte strings raise a sanitized protocol error. The list uses `data` only, including a JSON-text list accepted by the source JSONObject/Gson path; `array` is not a list fallback. Source Gson optionality is tightened deliberately for a usable typed read model.

`CodeChallenge` has state plus hidden image ID/image bytes text. Dynamic images use **`imgData`**, not image-fetch `imgCodeImgData`. Missing/malformed challenge data fails safely; code200 discards data. Source object `data`/`array` fallback and JSON-text objects are decoded with duplicate-member/nonfinite rejection. No image encoding, challenge lifetime or server code expiry is invented.

AccountClient alone enforces the original operation deadline. No retry, redirect following, origin adoption, DC cache adoption or automatic replay occurs. A constructed write is conservatively considered possibly dispatchable. Any later local/transport/protocol failure, including timeout, cancellation or quarantine, returns UNKNOWN_OUTCOME; this can include a failure before actual bytes leave the child, because the existing boundary does not expose an authoritative dispatch marker. A validated HTTP/business rejection returns REJECTED. A pre-construction scope/input error remains a closed AccountClientError with discarded exception context. Reads retain existing error behavior. Quarantine stays owned by the shared AccountClient.

## Key acquisition, ownership and rotation

`KeyBinding(scope: AccountScope, identity: TvtIdentityRef, generation: int, token_id: str)` must carry a linked identity, exact region/brand, positive USER credential generation and nonempty source token-ID. `SecurityKeyState(binding, token, config)` revalidates these fields and captures independent scope copies plus an internal digest associating the actual USER token bytes. It does not derive an AES key from the USER token.

The server-only `SecurityKeyConfig.temporary_key(binding) -> bytes` port supplies exact temporary key text. For password login this is lowercase MD5 of the raw old password encoded as ASCII; configured provider login uses its source MD5(code), while registration preparation is a separately scoped flow. For a source key rotation it may supply previous admitted **key text**, retrieved from a protected vault only after current identity/generation/lineage checks. There is no default genuine key, registration constant, global SDK getter or plaintext key persistence in this adapter.

The next worker must capture `data.sid` and `data.tokenId` from the actual accepted login/renewal operation while its raw response is still private. Existing `AccountTokens` does not expose them. Wire extraction and credential admission therefore need a separate reviewed protected path; this adapter does not fabricate sid, infer it from a token, or claim that acquisition is already integrated. After current protected credential admission, construct the corresponding KeyBinding and invoke `key_state.admit(binding, token, response: AccountResponse)`. Admission re-parses the bounded original reply, checks status consistency and requires HTTP2xx/business200, matching nonempty token-ID, nonempty canonical/aligned sid ciphertext and a valid resulting key. A privately constructed successful AccountResponse is still not an authority grant.

Native math uses the trailing-`=` heuristic: sid ending `=` is decoded as canonical Base64; otherwise its bytes enter the native encode/decode normalization unchanged. Temporary key text ending `=` is decoded; otherwise its raw bytes are the AES key. Only16/24/32-byte material is accepted. The source helper decrypts ECB blocks, zero-extends incomplete ciphertext and returns Base64 of all decrypted aligned bytes without unpadding or trimming NULs. `derive_key_text` retains that source math for private comparisons; state admission rejects incomplete ciphertext and invalid final material. A24-byte unpadded Base64 representation contains32 text bytes, which the native heuristic uses as a32-byte raw key.

An admitted matching nonempty token-ID retains its key when a changed, structurally valid sid arrives. Empty/malformed sid, rejected business responses, mismatched scope/identity/brand/region/generation/token bytes/token-ID or failed derivation terminally close the state. No failed setter can reload old persisted bytes. Successful admission drops temporary references. A changed generation or token association requires a new KeyBinding and fresh state: the worker must explicitly supply the correctly scoped previous key text when source rotation requires it. This module supplies no vault serialization, restore/export endpoint or global previous-key fallback; any future persistence must seal private key text with the complete binding and enforce current protected admission before retrieval.

`encrypt(binding, token, raw_password)` encrypts the32 ASCII bytes of lowercase MD5(raw UTF-8 password) using admitted AES-ECB and emits standard Base64. Original instructions use `FRINTP`: output length is `4*ceil(n/3)`, giving44 characters for the32-byte password ciphertext. No PKCS7 unpadding/padding is introduced. `update_password` checks key binding against the actual AccountClient context before request construction and closes the state on every terminal return or failure. `close()` removes references; memory zeroing and native hard termination of key material are not claimed.

Scoped Ruff, formatting, strict mypy and the concretely affected fixed-path/shared-boundary regressions are recorded with native exits and dependency hashes. These are invented local fixtures, not Android, vendor, remote account or server acceptance.

The later protected worker must issue/redeem/check current T03 actor, membership, consent, identity, grant and credential generation; bind stage/purpose/account/image state and a durable write intent; commit before HTTP; and resolve publication/readback. Success acknowledgement requires fresh profile and login-type reads before a persisted change is claimed. Profile cannot prove changed-password login or server-wide revocation. Server challenge consumption/TTL, real sid admission, remote profile/type permissions, contact login viability and password revocation remain authorized runtime acceptance work. Multipart/avatar, provider, QR, native unbind and account removal dispatch are separate scopes. No API/UI/RPC/database/startup integration is delivered here.
