# Wisdom Super Observer: Repository Analysis

**Date:** 2026-09-27 (Asia/Seoul)
**Scope:** The tracked repository contents at `main`, not a live-system assessment.
**Review method:** Three read-only subagents reviewed architecture, external integrations, and product requirements in parallel. The main agent independently checked their material findings against the source files, verified repository status and the specification hash, and performed the final review. The main agent authored this report.

## Executive assessment

Wisdom Super Observer is a detailed **pre-implementation plan** for a multi-tenant unmanned-store platform. Its intended scope combines sales analytics, product intake and registration, camera-based incident candidates, AI-assisted summaries, mobile alerts, human-approved broadcasts, and cautious visit-to-payment matching. The plan contains useful authorization, idempotency, evidence, and uncertainty rules. It does not yet establish that the external integrations or the proposed deployment architecture work on the intended accounts and devices.

The immediate critical path is to reconcile the controlling documents, record evidence for the external capability gates, and complete the mandatory SuperLive Plus APK static analysis. A product-and-sales pilot can then be defined separately from the full CCTV release. Application implementation has not started.

## Priority findings

### P0 — Reconcile document authority and release definitions

The current source hash differs from the one recorded by the implementation plan. More consequentially, `SERVICE_PLAN.md` still describes an initial GPT-only/web-login approach, while the detailed plan explicitly records a later instruction to use Codex CLI or Claude CLI and no direct API client. The Korean sales section names trading-day velocity; the English appendix omits it, while the detailed plan requires three distinct velocity denominators. These are specification-maintenance issues, not evidence that either implementation exists. Update the canonical requirement text, record the override/decision, and refresh the source hash before implementation briefs are issued. [Service plan, lines 36-37](../../SERVICE_PLAN.md#L36), [1251-1258](../../SERVICE_PLAN.md#L1251); [plan, lines 19 and 62](../superpowers/plans/2026-09-21-wisdom-super-observer-implementation-plan.md#L19), [514-525](../superpowers/plans/2026-09-21-wisdom-super-observer-implementation-plan.md#L514).

The source MVP says an Autonat **or** Tapo camera is sufficient, but the later detailed plan makes SuperLive Plus APK research and TVT runtime follow-through mandatory for full CCTV completion. The source puts product registration in Phase 7 and leaves MVP inclusion undecided; the detailed plan proposes text registration as the first usable slice. Define separate, named gates for a product/sales pilot and the full release, then decide whether registration belongs in each. A Tapo-only pilot must not be reported as completed TVT work. [Service plan, lines 596-641](../../SERVICE_PLAN.md#L596); [plan, lines 80-99](../superpowers/plans/2026-09-21-wisdom-super-observer-implementation-plan.md#L80), [1536](../superpowers/plans/2026-09-21-wisdom-super-observer-implementation-plan.md#L1536).

### P0 — Prove the external contracts on the intended systems

The plan's G01-G11 gates are the right framework, but the capability registry and sanitized live evidence do not exist yet. The highest-priority probes are:

1. **OrderQueen reads (G01):** verify an authorized account and store scope; exact request parameters, pagination, source IDs, timezone, session expiry, and agreement with a known sales period. The listed internal endpoint names alone are not a live contract. [Plan, lines 168-170](../superpowers/plans/2026-09-21-wisdom-super-observer-implementation-plan.md#L168), [490-506](../superpowers/plans/2026-09-21-wisdom-super-observer-implementation-plan.md#L490).
2. **OrderQueen new-product save (G02):** inspect required form fields, duplicate behavior, catalog scope, and POS effects. A specifically scoped real save requires readback of the frozen fields. An uncertain response must retain the write hold until authoritative reconciliation; a mock test does not prove site behavior. [Plan, lines 171](../superpowers/plans/2026-09-21-wisdom-super-observer-implementation-plan.md#L171), [537](../superpowers/plans/2026-09-21-wisdom-super-observer-implementation-plan.md#L537); [checklist, lines 107-118](../../PREPARATION_CHECKLIST_KO.md#L107).
3. **Required SuperLive Plus/TVT work (G10):** first obtain the authorized complete APK set or installed device and produce the version/hash/ABI inventory plus evidence-backed Java/JNI/native call map (T00A). Then separately establish live P2P login, channels, decodable video, alarms, teardown, and reconnect on the intended equipment (T31). Static symbols, public `pytvt` research, and Tapo playback cannot substitute for runtime proof. [Plan, lines 634-648](../superpowers/plans/2026-09-21-wisdom-super-observer-implementation-plan.md#L634), [1488-1512](../superpowers/plans/2026-09-21-wisdom-super-observer-implementation-plan.md#L1488).

Other gates remain site or device specific: wholesale login/session renewal and order parsing (G03); exact Tapo model, RTSP/ONVIF stream and reconnect (G05); CLI image-to-schema output under the intended account (G06); and a separately observed audible talk test (G07). Off-site media also requires decoded playback with store ingress blocked, forced relay, a UDP-blocked HLS fallback, and revocation during an active session. [Plan, lines 172-180](../superpowers/plans/2026-09-21-wisdom-super-observer-implementation-plan.md#L172), [235-241](../superpowers/plans/2026-09-21-wisdom-super-observer-implementation-plan.md#L235).

### P1 — Keep uncertain visual and transaction results reviewable

Freezer contact, running, waving, and kiosk difficulty depend on camera perspective, calibration, pose quality, track continuity, and actual store examples. The proposed precision and false-alert targets are **pilot goals**, not measured results. Payment matching must account for concurrent shoppers, camera and POS clock offsets, cancellations, and incomplete sales coverage. Time proximity is only `PAID_LIKELY`; `PAID_CONFIRMED` needs a deterministic source link or a human decision whose provenance remains visible. Without a verified payment-error event, label visual behavior as kiosk difficulty. Without historical stock observations, stock effects stay unknown. [Plan, lines 545-549](../superpowers/plans/2026-09-21-wisdom-super-observer-implementation-plan.md#L545), [579-587](../superpowers/plans/2026-09-21-wisdom-super-observer-implementation-plan.md#L579), [1526-1532](../superpowers/plans/2026-09-21-wisdom-super-observer-implementation-plan.md#L1526).

### P1 — Complete the data lifecycle and operating decisions

The checklist explicitly labels 14/7/7/180-day retention values as proposed defaults and asks the owner to decide before real video or photo intake. The plan also introduces transaction history, person tracks, visit sessions, payment matches, summaries, feedback, and model-training exports. Record a data-class retention/deletion matrix, including derived records and backup expiry, before a real-data pilot. Confirm who may download original evidence, which managers may broadcast, and whether every product batch receives pre-submit review. [Checklist, lines 318-344](../../PREPARATION_CHECKLIST_KO.md#L318); [plan, lines 273-288](../superpowers/plans/2026-09-21-wisdom-super-observer-implementation-plan.md#L273), [1438-1459](../superpowers/plans/2026-09-21-wisdom-super-observer-implementation-plan.md#L1438).

### P2 — Measure capacity before fixing the deployment shape

The proposed stack includes separate API, browser, media, AI, notification, edge, relay, database, queue, identity, object storage, and observability components. Its release versions are dated planning observations, not an installed compatibility set. Lock and test the actual dependency combination in T01; derive GPU, storage, bandwidth, CLI concurrency, recovery, and hosting needs from a small authorized pilot. The plan itself calls for this measurement rather than a guessed purchase. [Plan, lines 145-151](../superpowers/plans/2026-09-21-wisdom-super-observer-implementation-plan.md#L145), [186-249](../superpowers/plans/2026-09-21-wisdom-super-observer-implementation-plan.md#L186), [1562-1568](../superpowers/plans/2026-09-21-wisdom-super-observer-implementation-plan.md#L1562).

## Recommended sequence

1. **Correct the specifications:** reconcile CLI/provider language, release gates, registration review policy, sales metric definitions, and the recorded source hash. Keep proposed engineering choices distinct from confirmed product requirements.
2. **Collect the minimum real inputs:** an authorized installed SuperLive Plus app or complete APK set; a designated OrderQueen test store and known sales period; one first wholesale site with product/order examples; confirmed barcode, item name, unit and retail price examples; exact camera models and a scoped test setting. The user checklist does not ask the owner to decompile APKs, discover internal API parameters, or install the whole toolchain. [Checklist, lines 15-26](../../PREPARATION_CHECKLIST_KO.md#L15), [433-442](../../PREPARATION_CHECKLIST_KO.md#L433).
3. **Run T00/T00A and record evidence:** create the capability register, preserve unsupported and untested states, complete the mandatory APK static report, and keep live device/save/broadcast validation separate. Independent foundation work can proceed while device inputs are pending. [Plan, lines 617-648](../superpowers/plans/2026-09-21-wisdom-super-observer-implementation-plan.md#L617).
4. **Build and verify the foundation:** T01-T05A, especially tenant/store isolation, scoped workers, encrypted credentials, durable jobs, and private assets. Record actual test output in the proposed implementation ledger. [Plan, lines 650-809](../superpowers/plans/2026-09-21-wisdom-super-observer-implementation-plan.md#L650).
5. **Choose a named pilot gate:** deliver verified sales read and metrics, then text registration only after G02 and the product review decision. Label this a product/sales pilot if camera, mobile, broadcast, payment, or TVT requirements remain open. [Plan, lines 83-99](../superpowers/plans/2026-09-21-wisdom-super-observer-implementation-plan.md#L83), [1536](../superpowers/plans/2026-09-21-wisdom-super-observer-implementation-plan.md#L1536).
6. **Expand to full CCTV scope:** validate the standard camera and off-site media path, measure behavior quality, connect alerts/mobile/CLI and human-approved broadcast, and complete T31's TVT runtime evidence before declaring the full release complete.

## Final-review conclusion

The three parallel reviews agreed with the main agent's independent checks on the pre-implementation status, source-hash drift, unverified integration gates, and the need to separate partial pilot acceptance from full scope. The main agent spot-checked their cited source sections and verified the file inventory and SHA-256 independently. This report makes no claim that application tests, live account probes, device trials, or performance benchmarks have passed.
